# Архитектура

## Главная идея

**Игра — это пакет с манифестом** (`game.json`). Хаб не знает, чем игра собрана —
Phaser, Three.js, Godot, Rust→WASM или голый HTML. Он знает манифест и умеет три вещи:
показать игру, запустить её в песочнице и дать ей SDK.

## Компоненты

```
                 ┌─────────── games.youranus.ru ───────────┐
 браузер ──────► │ apps/hub (Next.js) — этап 0б            │
                 │ каталог · страница игры · позже админка │
                 │ packages/hub-bridge: протокол с игрой   │
                 └───────┬─────────────────────────────────┘
                         │ <iframe sandbox src=https://<id>.play.youranus.ru/>
                         │ postMessage (docs/SDK.md)
                 ┌───────▼──────── *.play.youranus.ru ─────┐
                 │ apps/play-server                         │
                 │  <id>.play…  → файлы текущей версии игры │
                 │  play…       → /exports/*.zip, /covers/* │
                 │  заголовки песочницы (docs/SECURITY.md)  │
                 └───────┬─────────────────────────────────┘
                         │ читает
                 ┌───────▼─────────────────────────────────┐
                 │ GF_DATA_DIR (.data/)                     │
                 │  registry.json          реестр           │
                 │  storage/games/<id>/<version>/  файлы    │
                 │  storage/exports/<id>-<version>.zip      │
                 └───────▲─────────────────────────────────┘
                         │ пишет
                 ┌───────┴─────────────────────────────────┐
                 │ tools/gf.ts: validate → build → export   │
                 │ games/<id>/game.json + исходники         │
                 └──────────────────────────────────────────┘
```

| Компонент | Что делает | Зависимости |
|---|---|---|
| `packages/manifest` | тип `GameManifest`, валидатор, JSON Schema для редактора | нет |
| `packages/registry` | реестр (`registry.json`), раскладка хранилища, атомарная запись | нет |
| `packages/game-sdk` | SDK внутри игры: режимы `hub` / `standalone` | нет |
| `packages/hub-bridge` | сторона хаба: проверка сообщений, лимиты, хранение | нет |
| `apps/play-server` | раздача игр по поддоменам, служебный хост | нет |
| `tools/gf.ts` | CLI: проверка, сборка, публикация, офлайн-архив | нет |
| `apps/hub` | каталог и страница игры | Next.js (этап 0б) |

Всё ядро — **без npm-зависимостей** (D-013): меньше поверхность атаки на «грязной»
стороне и нечему ломаться при обновлениях.

## Жизненный цикл игры

1. **Исходники** — `games/<id>/`: `game.json` + папка `source` (статика) или проект
   со скриптом `build` (Vite и др.).
2. **Проверка** — `gf validate`: манифест строгий, неизвестные поля — ошибка (ловит опечатки).
3. **Сборка** — `gf build`: для сборочных toolchain запускается `pnpm run build`, затем
   файлы собираются из `output`. Отвергаются симлинки, скрытые файлы, выход за лимиты.
   Если HTML ссылается на `gf-sdk.js`, SDK подкладывается в сборку.
4. **Публикация** — файлы кладутся в `storage/games/<id>/<version>/` атомарно
   (временная папка + rename), рядом `<version>.meta.json` с хешем содержимого.
   Та же версия с другим хешем — отказ (D-015). Реестр переключает текущую версию.
5. **Офлайн-архив** — `gf export` для `offline: true`: статическая проверка граблей
   `file://`, детерминированный zip (`<id>-<version>/…` + `README.txt`).
6. **Раздача** — play-server читает реестр (кеш по mtime) и отдаёт текущую версию.

## Домены и origin

| Что | Прод | Локально |
|---|---|---|
| Хаб | `https://games.youranus.ru` | `http://localhost:3000` |
| Игра | `https://<id>.play.youranus.ru` | `http://<id>.play.localhost:4100` |
| Служебный хост игр | `https://play.youranus.ru` | `http://play.localhost:4100` |

Каждая игра — отдельный origin: свои `localStorage`, cookies, Service Worker, и XSS в одной
игре не достаёт до других. Хаб и игры сейчас на одном регистрируемом домене —
это осознанный компромисс до открытия платформы (D-010, SECURITY.md, PITFALLS.md).

## Протокол хаб ↔ игра

Коротко: игра шлёт `hello`, хаб отвечает `welcome` (игра запоминает origin хаба), дальше
запросы `save / load / submitScore / bestScore` с ответами по `id`. Если хаба нет
(офлайн-архив, прямой заход), SDK за 1,5 с переходит в `standalone` и хранит всё в
`localStorage`. Подробно — [SDK.md](SDK.md).

## Хранилище: сейчас и потом

| | Этап 0 | Этап 1–2 |
|---|---|---|
| Реестр | `registry.json` | Postgres (таблицы `games`, `game_versions`) |
| Файлы | диск, `GF_DATA_DIR` | S3: MinIO локально или свой S3 по профилю хранилища |
| Сохранения и очки | `localStorage` хаба | API хаба + Postgres, лидерборды в Valkey |

Раскладка ключей в S3 повторяет пути на диске (`games/<id>/<version>/…`, `exports/…`),
поэтому переезд — это замена адаптера в `packages/registry`, а не переделка.

## Целевая архитектура (этапы 2–5)

- **Админка** в хабе: загрузка zip или git, версии, публикация и откат.
- **Builder** — сборка чужого кода в изолированном контейнере (gVisor, без сети, кроме
  зеркала npm), очередь задач на BullMQ (D-006).
- **Game Runtime** — контейнеры игр с бэкендом: любой язык, свой Dockerfile, лимиты,
  закрытый выход в сеть, короткоживущий токен вместо ключей хаба.
- **ИИ-студия** — шаблоны (`templates/`) + наборы скиллов (`skill-packs/`), агент на
  Claude Agent SDK внутри песочницы Builder'а, результат — коммит в репозиторий игры,
  дальше обычный конвейер.
- **Разделение машин**: доверенная (хаб, БД, S3) и «грязная» (Builder, Runtime).
  Пока всё на одном VPS (D-011).

Подробно по этапам — [ROADMAP.md](ROADMAP.md).
