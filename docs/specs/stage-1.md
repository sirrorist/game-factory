# Спецификация: этап 1 - хаб "по-взрослому"

> Сессия №6 (VPS-1, 2026-09-30). Кода нет. Решения владельца Р1-Р5 - ниже (D-047).
> Прочитать до правки: `CLAUDE.md`, `docs/STATE.md`, `docs/SECURITY.md`, `docs/PITFALLS.md`
> (П-005, П-006), `docs/ARCHITECTURE.md`, этот файл.

## Цель

У хаба появляются учётная запись и серверное состояние: владелец входит в хаб, сохранения и
очки вошедшего игрока живут на сервере, а не в `localStorage` браузера; очки проходят
серверную проверку правдоподобия. Гость (D-024) работает как сейчас.

**Не цель:** админка и загрузка игр, вход игроков и письма, 2FA, реестр в Postgres, Valkey и
очередь задач, файлы игр в S3 (всё - этап 2); отдельный домен игр (этап 5). S3 в этапе 1 -
только для бэкапа базы (Р5).

## Ограничения, которые задают форму

1. **Прод изолирован (D-038):** у хаба нет выхода в интернет. Значит, в этапе 1 не работают:
   вход через Google/GitHub (OAuth ходит наружу), письма (подтверждение почты, сброс пароля),
   любые внешние API. Нужен любой из них - это решение про D-038, а не правка compose.
2. **Ядро без зависимостей:** `apps/play-server`, `tools/`, `packages/registry` не получают
   драйвер Postgres. Что бы ни решили про реестр, сервер игр и `gf` его не читают из базы
   без отдельного решения.
3. **Данные перестают быть воспроизводимыми:** учётки, сохранения и очки не восстановить из
   образов. Пункт ROADMAP "бэкапа тома нет - осознанно" с первым же пользователем перестаёт
   быть правдой: бэкап базы - часть этапа, а не "потом".
4. **Ресурсы сервера ограничены.** Сколько памяти можно отдать базе - см. приватную базу
   инфраструктуры (D-043); здесь - только решение, сколько сервисов добавляем.
5. **Сервер игр и игры не видят базу.** Postgres - во внутренней сети только с хабом;
   `play` и `games` в неё не входят (SECURITY.md, "Сборка и контейнеры").

## Решения (владелец, 2026-09-30; D-047)

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| Р1 | Реестр игр в Postgres в этапе 1? | **Нет, в этапе 2** вместе с админкой. В этапе 1 Postgres хранит только учётки, сохранения, очки | реестр пишет `gf` в CI и читает сервер игр - оба без зависимостей (ограничение 2); переезд сейчас - драйвер в ядро или второй источник правды |
| Р2 | Лидерборды - Valkey или Postgres? | **Postgres** (индекс по `(game_id, score)`), Valkey - на этапе 2 вместе с BullMQ (D-006) | топ-N по индексу на нашем масштабе мгновенный, а лишний сервис - память и ещё один бэкап |
| Р3 | Кто входит в этапе 1? | **Только владелец.** Игроки и письма (подтверждение, сброс пароля) - этап 2 | без почты у игрока нет сброса пароля; владельца заводит команда на сервере |
| Р4 | Чем входит владелец? | **Пароль + passkey** (Better Auth); **2FA** - добавить в этапе 2 | passkey не ходит наружу и не фишится; пароль - запасной путь |
| Р5 | Бэкап базы | **в бакет S3** - через уже работающий бэкап сервера (ниже); проверка восстановления из бакета - критерий слайса 1.1 | данные невоспроизводимы (ограничение 3); бакет - вне сервера |

### Что следует из Р5

- **Встраиваемся в бэкап сервера, а не заводим свой.** У сервера уже есть ежедневный бэкап
  в холодный бакет S3 с шифрованием на стороне сервера (как устроено - приватная база
  инфраструктуры). Дамп нашей базы снимается командой
  внутри контейнера `db` и ложится туда же. Итог: **ни у одного нашего контейнера нет выхода
  в сеть** - D-038 не трогаем, ключей S3 в нашем проекте нет вовсе.
- **RPO этапа 1 - сутки** (так ходит бэкап сервера). Данные этапа 1 - только владелец, этого
  хватает. Горячий бакет (реплика с RPO в секунды-минуты) - когда появятся игроки (этап 2).
- **Бакет бэкапов - не бакет игр** (D-048): игры раздаются наружу, бэкапы - никогда.
- Что нужно от нашего репозитория: имя контейнера и команда дампа - в `docs/OPERATIONS.md`;
  проверка восстановления - на чистый том, с командой и итогом в STATE.

## Слайсы

Каждый слайс: свой коммит в `dev`, `pnpm check` зелёный, **роль "Безопасность"** на его diff
(`.claude/agents/security.md`) - находки закрыты или записаны как ⚠️ в SECURITY.md с "да"
владельца. Негативный тест каждой новой меры проверен мутацией (`docs/TESTING.md`).

### 1.1 База: Postgres + Drizzle, без функций

- `apps/hub`: Drizzle, схема и миграции в `apps/hub/db/`; миграции идут отдельным шагом
  (одноразовый контейнер, как `games`), не при старте хаба.
- Локально: Postgres в `docker-compose.yml`; e2e поднимают базу сами.
- Прод: сервис `db` в `deploy/compose.prod.yml`, своя сеть `gf-db` с `internal: true`, в ней
  только `hub` и `db`; том `gf-db`; ужесточение как у остальных (`cap_drop`, лимит памяти,
  без портов наружу). Пароль базы - файл-секрет compose, ввод владельцем скрытый.
- Бэкап по Р5: дамп в бэкапе сервера (блоком владельцу); восстановление - из бакета.
- **Критерии:** хаб стартует и отвечает на `/healthz` только при живой базе (иначе - 503, а
  не пустой каталог); `play` не резолвит и не достаёт `db` (зонд, как в D-038); восстановление
  из бакета на чистый том проверено и записано в STATE командой и итогом.

### 1.2 Вход владельца

- Better Auth: пароль + passkey (Р4), владелец заводится командой (`gf-admin create-owner`
  внутри контейнера хаба, пароль - скрытым вводом, правило кита).
- Кука сессии `__Host-gf-session`: `Secure`, `HttpOnly`, `Path=/`, без `Domain`,
  `SameSite=Lax` (П-006 - игры не перезапишут; SameSite - не защита от CSRF, П-005).
- CSRF: на каждый изменяющий запрос - токен **и** `Origin` = origin хаба; запрос без `Origin`
  отвергается. Проверка - в одном месте (middleware), а не в каждом обработчике.
- Лимит попыток входа.
- **Критерии (e2e):** вход и выход; кука с нужными атрибутами; запрос с `Origin` игры
  (`https://snake.play…`) и с правильной кукой - 403; кука с тем же именем, поставленная
  с поддомена игры, не принимается; мутации "без проверки Origin", "кука без `__Host-`"
  краснеют.

### 1.3 Сохранения и очки через API хаба

- `hub-bridge` не меняется: меняются обработчики `save / load / submitScore / bestScore` в
  `game-frame.tsx` - у вошедшего они ходят в API хаба, у гостя остаются в `localStorage`.
- API принимает запросы **только от страницы хаба** (CSRF из 1.2); из iframe игры API
  недоступен - игра по-прежнему говорит только с мостом.
- Лимиты моста (64 КБ, 20 запросов/с) повторяются на сервере: мост - не граница доверия
  для API.
- **Критерии (e2e):** сохранение вошедшего переживает очистку `localStorage` и другой
  браузер; гость как раньше; прямой запрос к API из контекста игры отвергается.

### 1.4 Лидерборд и проверка очков

- Лидерборд по Р2, в хабе на странице игры.
- Правдоподобие: в `game.json` - необязательный предел (`score.max`, `score.perSecond`),
  схема и валидатор - `packages/manifest` (ядро, без зависимостей); сервер отвергает очки
  выше предела и чаще лимита. Нет предела - принимаем, но помечаем как непроверенные.
- **Критерии:** очко выше `score.max` - отказ и запись в журнал; мутация "предел не
  проверяется" краснеет; SECURITY.md "Очки проверяются на сервере" - ✅ с тестом.
