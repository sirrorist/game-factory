## Четыре замечания ревью: выполненные изменения

| Замечание | Изменение и проверка |
|---|---|
| Окно 24 часа только перед клиентом | Служебный X-GF-Mail-Expires-At = createdAt + 24 часа, неизменный при повторе. Обязателен ровно один корректный заголовок; будущее более 24 часов отвергается. Остаток уменьшает таймаут клиента. На шлюзе фиксируется монотонный предел до чтения тела; перед каждой попыткой проверяются он и абсолютный срок. Полная попытка, а при повторе также пауза, должны помещаться до конца окна с резервом 1 секунда. Иначе unknown/operation_expired без нового upstream |
| Очередь pipeline в Node | dropRequest отменяет операцию соединения и немедленно закрывает сокет. Тест удерживает первый upstream, отправляет второй запрос и ждёт закрытия/отмены, без установки тестового обработчика dropRequest |
| Потеря статуса/Retry-After при обрыве ответа | io сохраняет статус и ограниченный ASCII Retry-After при oversized/truncated/timeout после заголовков, возвращая признак incomplete и пустое тело. Provider возвращает unknown без повтора, безопасно разбирает Retry-After. Ошибки до получения заголовков сохраняют прежнюю ограниченную политику |
| Негативный тест потокового размера | Незавершённое chunked-тело без Content-Length превышает 16 КиБ. Проверяется 400 и закрытие в пределах 1 секунды при body timeout 10 секунд; JSON-парсер не может подменить потоковую проверку |

Проверки окна покрывают истечение во время первого вызова и паузы, недостаточный
остаток и скачок часов назад; клиент сохраняет исходный срок между вызовами.
Loopback HTTP покрывает отсутствующий/невалидный/дублированный срок, истёкшую
операцию и пересечение границы на шлюзе. Ошибки ответа проверяются для обеих форм
oversized/truncated и обоих статусов 502/429 с Retry-After: 60, ровно один вызов.

Срок операции — доверенный служебный контекст хаба, не пятое поле письма и не часть
payload Resend. Вызывающий обязан хранить исходный createdAt вместе со снимком.
Для будущего размещения нужны согласованные часы хаба/шлюза в пределах секундного
резерва; реальная синхронизация не проверена. Монотонный предел не продлевается
при переводе часов назад в текущем вызове. Отмена не отзывает уже принятый запрос
провайдера; глобальная гарантия доставки/дедупликации за его окном не заявляется.

Прежняя согласованная правка сохранена: неизвестные 500–599 возвращают unknown без
автоповтора; распознанные application_error (500) и service_unavailable (503)
сохраняют ограниченную политику. Тест неизвестных 500/502/504 ранее краснел на старом коде.

## Согласованное уточнение старого теста общего дедлайна

apps/mail-relay/test/http.test.ts, «общий дедлайн отменяет медленный upstream без
оставшихся попыток»: assert.rejects(call(...)) иногда даёт Missing expected rejection.
Значит клиент получил HTTP-ответ вместо требуемого тестом разрыва сокета.
Прежний TAP сохранял имя/строку/ошибку; тело ответа в нём не записывалось.
Это может объяснять прежний промежуточный отказ 48/49, но тождество не доказано.

По коду ограниченная upstream-попытка может завершиться таймаутом раньше таймера
закрытия всего соединения и позволить шлюзу отправить структурированный unknown.
Это объяснение по исходникам, не наблюдение сохранённого HTTP-тела.
После отдельного разрешения владельца тест принимает только ECONNRESET либо
HTTP 503 с ровно полями outcome/code: unknown и cancelled/transport_error. Успех,
произвольная ошибка HTTP и собственный 1,5-секундный timeout клиента не принимаются.
Проверки count=1 и фактической отмены upstream сохранены. Код транспорта для этого
уточнения не менялся. Целевой прогон после изменения — 56/56.
