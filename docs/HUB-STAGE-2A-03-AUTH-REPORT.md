# 2А-03 A: локальная реализация

2026-10-28. Владелец утвердил только закрытый A после ревью
[плана](HUB-STAGE-2A-03-AUTH-PLAN.md) без находок; параметры — D-064.
Ни один рабочий секрет, адрес учётки или рабочая БД здесь не использованы.
Реализация опирается на локальный 2А-02, который не входил в почтовый коммит.

## Перепроверка трёх замечаний первого ревью

Владелец разрешил этот объём отдельно. Изменены только порядок headers и отказ
по timeout; логика токенов/SQL/очереди/диспетчера не переписывалась.

1. Общее правило Next теперь идёт перед специальным. Настоящий helper установленного
   Next unstable_getResponseFromNextConfig проверяет итоговые HTTP-заголовки обеих
   страниц и сохранение обычной политики остальных страниц. Обратный порядок
   даёт красный тест. Это проверка route matcher, не браузерный Referer capture.
2. Потоковые тесты для четырёх действий отправляют >4096 байт без Content-Length/EOF
   и незавершённое тело. Виртуальный timer проверяется на 4999/5000 мс, проверяются
   cancel, освобождение reader и отсутствие store/session/DB-вызовов.
   Дополнительно воспроизведён дефект: полный JSON без EOF после cancel по timeout
   мог перейти к обработке. Теперь timedOut отдельно запрещает разбор накопленного JSON.
3. На входе send другое настоящее PG-соединение читает committed started-запись,
   расшифровывает prepared-снимок и точно сравнивает body/createdAt с аргументом send,
   operationId с ID строки и kind с назначением. Проверены verify/reset. Ошибки
   assert вынесены за catch диспетчера и действительно проваливают тест.

Новые семь мутаций: обратный порядок headers, снятый предел bytes, отключённый
deadline, снятый отказ разбора после timeout, отсутствующий prepared-ciphertext,
другой body и другой createdAt. Все дают целевой testCodeFailure; три последние
исполнены на независимых backend PostgreSQL. Прежние 17 мутаций не повторялись:
их результаты сохранены как исторические, отдельно от recheck/mutations.json.
На прежнем коде новый тест headers и полный JSON без EOF красные (previous-tests.tap).

Новые HTTP-тесты включены в корневую проверку типов. Headers-helper и его Next-типы
проверяются отдельным apps/hub/tsconfig.auth-tests.json: глобальные декларации Next
не подключаются ко всем старым Node-тестам. Минимальный Node baseline загружается
до testing helper так же, как в серверном окружении установленного Next.

## Что реализовано

- Миграция 0003 добавляет auth_actions, auth_mail_operations, auth_mail_counters,
  auth_recovery_guards и границу auth_actions_not_before у user. Сохранения и
  рекорды не переписываются. Metadata получены drizzle-kit в отдельном каталоге;
  SQL-процедуры/триггеры добавлены явно. Миграции применялись только во временных БД.
- Token из 32 случайных байт, SHA-256 в таблице действия, назначение/email/generation,
  24 часа для verify и 30 минут для reset. Узкая SECURITY DEFINER-процедура принимает
  исходный bearer, перепроверяет его под блокировками, потребляет атомарно.
  Переданный hash из таблицы доказательством не является. NULL/чужое назначение закрыты.
- Reset только для active user/developer без обязательного усиленного фактора;
  проверка повторяется при потреблении. Меняет password hash, повышает поколение,
  отзывает сессии/passkey/старые ссылки и ожидающие отправки; emailVerified сохраняется.
  Проверка другой действующей сессии даёт conflict и не потребляет token.
  Подтверждение email не создаёт сессию и не меняет роль.
- auth_recovery_guards — закрытый операторский маркер обязательного фактора.
  Плагин TOTP в A не подключён. Будущий B обязан устанавливать/снимать этот маркер
  атомарно с изменением факторов; сам маркер не доказывает усиленный вход.
  Необязательный player-passkey не считается обязательным MFA и отзывается reset.
- Новые намерения не ищут user и не ждут HTTP-провайдера. Запросу соответствует
  серверное подписанное намерение на 24 часа; форма сохраняет его при повторе.
  Одинаковый intent не меняет получателя/назначение и не зависит от потери первой
  browser-cookie. После истечения нужен новый явный запрос формы.
- Очередь хранит зашифрованное намерение; при захвате сохраняет точный PreparedMail
  с прежними operationId/createdAt и профилем auth-mail.v1 перед первым HTTP.
  AES-256-GCM связывает ciphertext с ID/purpose/createdAt/profile/stage/key-id.
  Состояние started после сбоя становится unknown; повторного захвата/HTTP нет.
  На конечном исходе ciphertext удаляется. Отмена не доказывает отсутствие отправки.
- Если до начала HTTP отсутствует старый ключ/повреждён снимок, транзакция отказывает,
  исходная pending-запись остаётся для восстановления; нет plaintext fallback,
  нового ID или потери ciphertext. Диспетчер ограничен двумя заданиями процесса;
  захват в БД не позволяет двум процессам независимо отправить одну операцию.
- Отзыв/смена адреса устанавливает auth_actions_not_before. Намерение, поставленное
  до отзыва и ещё не связанное с userId/token, не получает свежую ссылку после него.
  Захват: access_lock → user → action/mail; обслуживание завершается отдельной
  транзакцией до user-lock. Сеть выполняется после commit.
- Счётчики постоянны: email — 60 секунд, 3 за скользящий час, 5 за UTC-сутки;
  browser — 10/час, IP или IPv6 /64 — 50/час; платформа — 70/UTC-сутки,
  2000/UTC-месяц. Ключи email/browser/IP — HMAC. Новые адреса и роли имеют ту же
  политику; видимый 429 зависит только от источника/общей вместимости.
  Пределы: 10000 счётчиков, 5000 операций, очистка не более 100 строк каждой
  области за проход. Живые счётчики не вытесняются ради новых.
- Четыре POST API, две страницы с формой запроса/потребления. GET лишь отображает
  форму; без автоматического входа/переадресации. Origin+CSRF проверяются также
  непосредственно в обработчике. Тела ограничены 4096 байт и пятью секундами чтения.
  Ответы no-store/no-referrer, страницы noindex; token не отражается в сообщениях.
- Штатные Better Auth send/verify/reset и их server API закрыты, включая GET callback.
  Нормализация входа и действий — trim + lowercase. LoginGuard и прежние F1–F4
  сохранены; adapter не получил общего разрешения от одноразового token.

## Флаги и ключи закрытого стенда

Все новые API/страницы выключены без GF_AUTH_ACTIONS_ENABLED=closed-test.
Диспетчер дополнительно требует GF_AUTH_MAIL_DISPATCHER=closed-test,
Node-runtime и отсутствие фазы сборки. Запуск через instrumentation возвращается
после установки ограниченного таймера; stop прекращает новые захваты и отменяет HTTP.
В существующий compose флаги/секреты не добавлены; рабочее включение не выполнено.

GF_AUTH_MAIL_KEY_FILE — отдельный бинарный файл ровно 32 байта. Для чтения старых
снимков поддержан ограниченный список GF_AUTH_MAIL_OLD_KEY_FILES; ключи не попадают
в relay/БД/браузер. При добавлении нового ключа последний сохранённый ключ остаётся
основанием HMAC счётчиков. Его преждевременное удаление изменит область счётчиков:
порядок/срок хранения и отдельный сценарий компрометации ключа должен утвердить
оператор до размещения; минимум покрывает все живые счётчики/намерения.
Это поддержка чтения key-ring, не готовая эксплуатационная процедура ротации.

## Непроверенное и следующие условия

- Next build/SSR и браузер, аппаратный WebAuthn, CI и собранный хаб с instrumentation
  не запускались. Юнит HTTP/тестовые P-256-подписи не заменяют эти проверки.
- Не проверены реальные email-коллизии, backfill, рабочие SQL-права/миграция,
  доставка recovery, журналы инфраструктуры и восстановление заполненной БД.
- Шифрованные pending-намерения и started/payload проверены тестами; завершение
  процесса между commit и HTTP принципиально остаётся unknown без автоповтора.
  Доставленное во время отзыва письмо физически не отзывается, его token недействителен.
- Полные факторы/step-up/recovery codes относятся к B; полная Q3/CSP/регистрация — C.
  До игроков нужны B/C, RBAC-совместимый откат и резервирование/восстановление D-047.
- Git, публикация, рабочая активация и ключи требуют следующих отдельных решений.
  Ревьюера запускает владелец по [промпту перепроверки](HUB-STAGE-2A-03-AUTH-RECHECK-PROMPT.md).
