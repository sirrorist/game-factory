# 2А-02 — локальная реализация ролей и проверок доступа

Дата первоначальной реализации: 2026-10-20. Исправления F1–F4: 2026-10-21.
Владелец разрешил этот шаг командой «го» после обсуждения плана
и исправления N1/N2 повторного ревью контракта. Последнее независимое статическое
ревью, переданное владельцем, не содержит находок. После него по отдельному «ок»
выполнен пакет проверок на временном PostgreSQL. **Готово к приёмке владельцем;
не применено к рабочей БД и не опубликовано.** Следующий шаг 2А-03 не начат.

Исходная копия файлов сохранена во временном каталоге до редактирования. Существующие
документы и UI-правки не откатывались. Git-команд и вызовов подагентов не было.
Проверяющего запускает владелец по [отдельному промпту](HUB-STAGE-2A-02-REVIEW-PROMPT.md).

## Поведение

- У учётки есть `user/developer/admin/owner`, `active/suspended` и поколение безопасности.
  Существующие учётки после расширяющей миграции получают `user`, без автоматического
  присвоения owner. Старые saves/scores и учётные данные сохраняются.
- Permissions фиксированы и централизованы; операции `.own` требуют текущего владельца
  ресурса. Admin не назначает роли и не блокирует admin/owner. Неизвестные значения
  не дают доступа. Это основа проверок, не активация будущих game/cloud API.
- Сессия хранит поколение безопасности. Изменение роли/статуса атомарно повышает его,
  удаляет сессии и пишет событие. SQL-триггер отклоняет создание/обновление сессии
  для заблокированной учётки или со старым поколением. После F1 поколение фиксируется
  **до проверки credential**, а защищённый adapter атомарно сравнивает его при записи.
  Прежнее утверждение о любом начатом до отзыва входе было ошибочным: hook брал
  новое поколение слишком поздно; исходные 45 тестов эту гонку не проверяли.
- Последнего active owner нельзя понизить, заблокировать или удалить, включая прямой SQL.
  Общая строка `access_lock` сериализует изменения; новый snapshot не предполагается
  автоматически после advisory lock. BEFORE STATEMENT берёт access_lock до строк user
  также для прямого SQL; row trigger не меняет порядок. Auth-запись берёт user до
  credentials/session. UPDATE session не берёт user-lock из строкового триггера и
  не может менять userId/id/generation. Конфликты 40P01/40001 повторяют всю транзакцию
  максимум трижды, с исходным доказательством входа; прочие ошибки не повторяются.
- Next-сессия повторно проверяется по БД. `/kit` и навигация проверяют `kit.view`,
  каталог/страница пререлиза — `prereleases.view.all`. Вошедший user больше не owner.
  Собственные пререлизы разработчиков и отдельные grants подключаются в 2А-04.
- HTTP-обработчики Better Auth отвергают клиентские поля прав; регистрация и
  `delete-user` остаются выключены. Создание сессии проверяет статус и поколение;
  старые cookie не оживают после разблокировки. Нет общего кеша прав/сессий.
- SQL-роль `gf_hub` не обновляет role/status/generation и не удаляет пользователей,
  не меняет `access_lock`/журнал. Создавать можно только обычного active user с
  начальным поколением: это проверяет INSERT-триггер, поскольку Drizzle перечисляет
  в INSERT и колонки с `DEFAULT`. Профиль и штатный вход с ограниченной ролью работают.
- Журнал сохраняет actor/target, прежние/новые права, поколение и причину, без паролей
  и сохранений. История не удаляется вместе с учёткой. Привилегированная trigger-функция
  не разрешена PUBLIC: её нельзя подключить к собственной таблице для подделки событий.
  После F4 custom GUC учитываются только у вызывающей SQL-роли с правами владельца
  access_events. Для gf_hub actor всегда system, actor ID пуст и причина фиксирована;
  SECURITY DEFINER не объявляет владельца самой функции автором операции.
- Аварийный `set-password` теперь выполняет смену пароля, повышение поколения,
  удаление сессий и passkey одной транзакцией. Новое MFA/recovery из 2А-03 ещё не реализовано.

## Операторский интерфейс и переход

Новые команды подготовлены, но не запускались на рабочей БД:

```text
node packages/db/src/admin.ts bootstrap-owner --email <явно выбранная почта> --reason <причина>
node packages/db/src/admin.ts set-access --email <почта> --role <роль> --reason <причина>
node packages/db/src/admin.ts set-access --email <почта> --status <active|suspended> --reason <причина>
```

Они требуют операторское подключение БД. `bootstrap-owner` работает только при
отсутствии назначенных owner; не выбирает учётку по имени, возрасту или количеству.
`create-owner` явно создаёт новую учётку owner; роли/статусы не принимаются профилем.
Библиотечные операции проверяют действующие права actor=user, но не подключены к
вебу; будущий веб-путь потребует step-up и отдельного узкого права записи в БД,
вместо выдачи хабу полного UPDATE служебных полей.

**До рабочей выкладки:** согласовать реальные owner, расширяющую миграцию и явный
bootstrap до переключения на новый код. Один автоматический прогон миграций
не сохранит прежнему вошедшему пользователю полномочия owner. Список владельцев
ещё не предоставлен. Откат к коду «вошёл = owner» после появления игроков запрещён.
Публикация, реальная миграция и bootstrap требуют отдельного разрешения.

## Исправления по независимому ревью F1–F4

- **F1:** снимок user/generation фиксируется до чтения пароля/ключа библиотекой.
  При session INSERT сравнивается этот снимок, а не актуальное поколение после сброса.
  Для passkey дополнительно проверяется существование именно исходного ключа.
- **F2:** account/passkey/profile/session записываются через общий защищённый adapter,
  включая прямой plugin adapter.create и adapter внутри transaction callback.
  В транзакции записи сначала блокируется user, затем проверяются исходные поколение,
  сессия, её срок и принадлежность цели. Криптография выполняется до блокировок.
  Без request-scoped доказательства запись закрыта; HTTP и server API имеют отдельные
  контексты AsyncLocalStorage. Новые способы входа/плагины потребуют отдельного допуска.
- **F3:** порядок блокировок исправлен в SQL и auth adapter; добавлен ограниченный
  повтор транзакций. Два исходных цикла описаны проверками настоящего временного
  PostgreSQL в READ COMMITTED/REPEATABLE READ. В последнем согласованном пакете
  все четыре выполнены на двух настоящих backend-соединениях PostgreSQL 17.11:
  операции завершаются, отзыв удаляет сессию, 40P01 не скрывается повтором.
  Отдельные два сценария last-owner оставляют одного активного owner; при старом
  snapshot REPEATABLE READ реально наблюдается 40001 и повтор всей операции.

- **F4 (P3):** подтверждена подмена новых событий через gf.access_actor_kind/id/reason.
  Триггер определяет вызывающую SQL-роль по встроенному role с учётом SET ROLE,
  либо SESSION_USER, если role не выбран. Custom GUC принимаются лишь при правах
  владельца таблицы журнала (pg_has_role USAGE); current_user внутри SECURITY DEFINER
  для этой проверки не используется. Приложение этих прав не получает.
  Отрицательный тест gf_hub с заявленными operator/user/invalid сохраняет только system,
  NULL actor ID и фиксированную причину. Положительный операторский контекст сохранён.
  На прежнем триггере тест красный (подставленный operator записан), после исправления
  проходит. Последний пакет дополнительно проверил отдельное настоящее подключение
  gf_hub: SESSION_USER/CURRENT_USER действительно gf_hub, смена SQL-роли на владельца
  запрещена, custom GUC не меняют автора. Штатные вход/профиль работают; INSERT owner,
  служебный UPDATE, DELETE user и прямая запись/удаление журнала отклоняются.

Четыре детерминированных HTTP-сценария F1/F2 проверяют задержку после чтения
старого credential либо перед INSERT passkey, сброс оператором и продолжение запроса.
На сохранённом auth-core до исправления **все четыре красные: HTTP 200 после сброса**;
на текущем коде все четыре проходят с отказом и без новой сессии/ключа. Пароль оператора
сохраняется. Используются реальные P-256-подписи и WebAuthn-ответы тестового
аутентификатора, без замены криптографической проверки на успех.

Дополнительно проверены штатные регистрация passkey с createSession, вход, server API,
refresh, выход, истечение сессии и смена пароля с revokeOtherSessions. При истечении
разрешено только удаление самой исходной строки сессии, без refresh/credential-write.
Отдельно инъекция SQLSTATE подтверждает полный откат, три попытки и отсутствие
повтора обычных ошибок; она не объявляется воспроизведением настоящего дедлока.

## Согласованный пакет после завершения статического ревью

Код приложения, DB-библиотека и миграции **в этом пакете не менялись**. Добавлены
проверки и вынесены общие тестовые функции в auth-race-fixtures.ts. Новых ошибок
реализации не обнаружено; самостоятельных исправлений и перехода к 2А-03 не было.

Временные бинарники PostgreSQL 17.11 распакованы только во временный каталог,
SHA-256 сверены с метаданными пакетов. Системная установка не выполнялась.
Кластер создан тестом с синтетическими данными и Unix socket; listen_addresses пуст.
Для сокета потребовался разрешённый запуск вне песочницы. Рабочие подключения,
.env и секреты не использовались. После прогона сервер остановлен, сокет отсутствует.

Две дополнительные отрицательные гонки выполнены на настоящем PostgreSQL:

- passkey/verify-registration с createSession=true задержан перед INSERT именно
  **внутри transaction callback**. Сброс выполнен вторым подключением; продолжение
  даёт 401, passkey и новая сессия отсутствуют;
- server API changePassword задержан перед проверкой сохранённого старого хеша.
  После сброса запрос отвергается, прежние сессии отсутствуют; пароль оператора
  принимает настоящий sign-in, пароль начатого запроса — нет.

## Непроверенное и следующие условия

- Проверены конкретные сценарии конкуренции на временном PostgreSQL 17.11,
  а не отсутствие всех возможных дедлоков. Произвольные прямые SQL-транзакции
  с предварительными блокировками должны соблюдать access_lock → user → credentials/session.
  Воспроизводимый тест принимает только каталог локальных бинарников,
  создаёт собственный кластер и не принимает URL рабочей БД.
- Полная браузерная WebAuthn-церемония после изменений. Проверен
  HTTP-проход с программным тестовым P-256-аутентификатором. Браузер, аппаратный ключ,
  Next SSR и переходы остаются для CI/e2e.
- Сборка Next, полный CI, публикация и рабочая инфраструктура не запускались.
  Игры, bridge/SDK, CSS, раскладка страниц, загрузчик и cloud API не менялись.
- MFA/почта/recovery/Q3 нового этапа, game ownership/grants/hosting, облако и экономика
  не объявляются реализованными этим шагом. D-047 о резервировании/восстановлении
  остаётся условием допуска игроков, а не результатом локальных тестов.

Следующее действие: приёмка владельцем результатов 2А-02. Последнее статическое
ревью реализации было без находок; после него менялись только тесты и документы. 2А-03 начинается только с отдельного плана и разрешения.
