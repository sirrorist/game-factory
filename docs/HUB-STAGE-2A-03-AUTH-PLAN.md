Основа: [общий план](HUB-STAGE-2A-PLAN.md), [политика Q2/Q3](HUB-USERS-ROLES-CONTRACT.md),

## 1. Исходное состояние и важные зависимости

- Почтовый пакет 32a3e24 опубликован. По переданному владельцем отчёту infra-ctl
  транспорт размещён, сетевые проверки пройдены, одно письмо принято и получено.
  Это сведения отчёта, не новое подключение текущего агента к VPS.
- Код ролей/поколений/guards 2А-02 остаётся отдельным локальным изменением:
  он не входил в почтовый коммит. Настоящие owner, backfill, миграция и включение
  RBAC на рабочей базе требуют отдельного согласования перед публикацией auth.
- Прочитан локально установленный Better Auth 1.7.7: email verification выпускает
  JWT и использует GET; само по себе это не даёт нашего одноразового серверного
  разрешения, связанного с поколением учётки. Reset использует verification-запись,
  но его последовательность не реализует весь согласованный атомарный отзыв.
  Это различие требований, не заявление об уязвимости библиотеки.
- auth-access.ts сейчас допускает credential-write по доказательству сессии,
  а anonymous email-reset требует отдельного узкого доказательства. Нельзя
  разрешить этому маршруту произвольные записи или снять защиту F1/F2.
- Один вызов sendVerificationEmail/sendResetPassword недостаточен. Нужен
  платформенный слой токенов/операций, встроенный в текущую auth-границу;
  Better Auth сохраняет password/passkey/session-механизмы и проверенный адаптер.

## 2. Порядок и поведение для пользователя

| Подшаг | Результат | Что разрешается отдельно |
|---|---|---|
| A. Подтверждение email и почтовый reset на закрытом стенде | Одноразовые ссылки, страницы, серверные операции и доставка через готовый relay. Reset пока только для user/developer без усиленного фактора | Утверждён только A; закрытые искусственные учётки и тестовая БД |
| B. Усиленный вход и полное восстановление | UV-passkey либо пароль + TOTP для admin/owner; недавнее подтверждение, резервные коды, ограниченное CLI-восстановление | Отдельный план и разрешение после A |
| C. Полная Q3, регистрация и защита браузера | Общая политика ограничений, регистрационные формы, CSP и проверки внешних рубежей | Порогам Q3, fail2ban и включению нужны решения владельца |
| D. Рабочее включение | Подтверждённые owner/backfill, миграции, бэкап/восстановление и поэтапная активация | Отдельные Git/dev/main, инфраструктура и допуск игроков |

Публичная регистрация в A/B остаётся закрыта. A не объявляется полным выполнением
Q2: обычная смена пароля с усиленным подтверждением и recovery admin/owner
заканчиваются в B. До B новые почтовые reset-маршруты не сбрасывают credentials
admin/owner или учётки с любым настроенным усиленным фактором. Отказ не раскрывает
роль через публичный ответ. Существующие вход и защиту не переключать незаметно.

## 3. Утверждённый объём закрытого A

### 3.1 Серверные токены

- Случайный token из 32 байт; в таблице действий хранится только SHA-256 token,
  назначение, userId, снимок нормализованного email, securityGeneration,
  срок и состояние потребления/отзыва. Token не используется как userId/роль.
- Утверждённые для закрытого A сроки: подтверждение email - 24 часа,
  reset - 30 минут. Это параметры продукта, не готовые свойства библиотеки.
- Новая явно запрошенная ссылка отзывает прежнюю для того же назначения.
  Двойной submit одной формы объединяется одним серверным ID намерения.
- Потребление и изменение учётки выполняются атомарно. Проверяются актуальные
  status, generation, email и назначение. Истёкший, отозванный или использованный
  token не получает новое поколение и не превращается в обычную сессию.
- Один и тот же token нельзя одновременно успешно применить дважды. Предварительная
  проверка перед дорогим хешированием не заменяет повторную проверку в транзакции.
- Нормализация едина для входа, запросов и token-снимка: trim + lowercase,
  без удаления точек/плюсов и специальных правил почтовиков. Для первого среза
  допускаются адреса, совместимые с ASCII-mailbox контрактом транспорта.
  Коллизии/неподдерживаемые старые адреса не исправляются догадкой: проверка
  рабочей базы и её решение возможны только перед отдельно разрешённым backfill.

### 3.2 Подтверждение email и reset

- Страницы сохраняют уже принятые адреса /account/verify-email?token=...
  и /account/reset-password?token=...; произвольные callbackURL не принимаются.
- GET показывает форму, не потребляет token: просмотр письма и почтовый сканер
  не выполняют подтверждение или смену пароля. Изменение только POST с Origin/CSRF.
- Подтверждение меняет emailVerified только по серверному разрешению и не выдаёт
  роль, административный step-up, новую login-сессию или доступ другой учётке.
- Reset в A для разрешённой учётки: новый hash, повышение securityGeneration,
  отзыв всех сессий/passkey, старых reset/enrolment/verification-разрешений и
  ожидающих чувствительных mail-операций в одной транзакции. Чужие данные игр
  не меняются. После успеха нужен новый вход; автоматического входа нет.
- Не ставить emailVerified=true в reset по побочному эффекту: подтверждение
  адреса остаётся отдельной явной операцией. Существующее истинное значение сохраняется.
- Наличие роли/фактора перепроверяется при самом reset: если после выпуска ссылки
  учётку повысили либо добавили MFA, старый упрощённый маршрут не применяется.
- В A не появится выдача/использование launch grants. До появления контекстов
  следующий этап обязан включить их в ту же границу отзыва; текущая модель
  generation уже не должна допускать старое доказательство после reset.
- Ссылка A, открытая при входе под B, не прикрепляется к B и не меняет её credentials.
  Для такого конфликта UI требует выйти/открыть чистую сессию; токен при отказе
  не потребляется. Подтверждение/сброс не переключают учётку автоматически.

### 3.3 Связь с Better Auth и БД

- Для новых действий - узкие платформенные POST routes и серверные функции.
  Пересекающиеся штатные send/verify/reset routes и server API не оставлять
  альтернативным путём с другими правилами. Отдельно проверить GET/callback-варианты.
- Существующий защищённый adapter не расширяется до «verification даёт все права».
  Одноразовое доказательство разрешает только конкретное действие и целевую учётку,
  не создание сессии/фактора, назначение роли или произвольный updateUser.
- Логика изменения находится в packages/db и использует принятый порядок
  access_lock -> user -> credentials/session/token/операции. Внешний HTTP не
  выполняется при удержании транзакционных блокировок. Ретраи 40P01/40001
  сохраняют первоначальное доказательство и не повторяют HTTP-отправку.
- gf_hub не получает общий UPDATE role/status/securityGeneration или запись
  журнала. Нужную операцию отзыва оформить ограниченной SQL-процедурой с
  проверяемым одноразовым основанием, фиксированным search_path и узким EXECUTE.
  Её нельзя использовать для подделки журнала оператора либо изменения другой учётки.
- Таблица verification библиотеки для собственных нужд passkey не отключается.
  Платформенные токены имеют своё назначение/хранилище и не принимаются за неё.

### 3.4 Подготовленная отправка и независимый внешний ответ

HTTP-ответ на запрос ссылки не должен ждать Resend и отличаться по тому, есть ли
учётка/роль, подтверждён ли email, заблокирован ли пользователь или исчерпана квота.
Сбой провайдера не выдаёт эти сведения через статус, задержку или тело.

Предлагается небольшая постоянная таблица auth_mail_operations в той же БД.
Она хранит подготовленную отправку: исходные operationId/createdAt, профиль,
связь с действием, состояния и зашифрованный снимок полного payload. Это новая
часть auth-плана, не свойство уже выпущенного транспорта.

- HTTP фиксирует намерение/лимиты в БД и возвращает единый ответ; нельзя ждать
  отправку для известного email и возвращать сразу для неизвестного. Внешний ответ
  не содержит userId, mail-operation ID или статус существования учётки.
- Диспетчер работает в существующем Node-процессе хаба с ограниченной конкурентностью
  и захватом операции в БД. Запуск через Node-only instrumentation, только при
  явном серверном включении; не во время build, не в Edge, не через публичный URL.
  Новый брокер/Valkey/BullMQ или отдельный сетевой сервис для A не предлагаются.
- Непереданные операции сохраняются при перезапуске. Захват и маркировка начала
  попытки атомарны; несколько экземпляров процесса не отправляют одну операцию
  независимо. Переходы исключают блокировку user после захвата mail-строки.
- На одну операцию - один вызов клиента relay; собственных скрытых повторов
  диспетчер не добавляет к двум upstream-попыткам шлюза. Падение после начала
  вызова даёт unknown; без доказательства результата новую отправку автоматически
  не создаём. Это сознательное ограничение доставки, а не гарантия exactly-once.
- Явный новый запрос пользователя после лимитов - новое намерение с отзывом
  старой ссылки. Он отличается от автоматического перевыпуска ID после unknown.
- Повторное использование подготовленной операции, если отдельно инициировано
  её продолжение, сохраняет весь ID/payload/профиль; для A автоматическое
  продолжение после начала вызова не предусмотрено. Созданное намерение
  не подменяется новым через сетевой retry или двойной клик.
- До вызова проверяются действительность действия и остаток срока ссылки/окна
  транспорта с резервом. Отзыв может пересечься с уже начатым HTTP: письмо
  физически не отзывается, но его token после отзыва не работает.
- Для encrypted payload предлагается отдельный 32-байтный ключ хаба из файла,
  AES-256-GCM с уникальным nonce и привязкой метаданных к ciphertext. Ключ не
  попадает в relay, БД, браузер и репозиторий. Потребуется отдельный инфраструктурный
  шаг перед размещением; не изменять сейчас секреты VPS или GF_AUTH_SECRET.
  При смене ключа не терять старые активные операции: key-id/срок хранения
  согласуются; невозможность расшифровки даёт отказ, не новый token/ID.
- SQL-читатель без этого ключа не должен получить готовые bearer-ссылки из таблицы
  доставки. После конечного состояния/истечения ciphertext удаляется ограниченным
  обслуживанием; безопасность срока обеспечивается проверкой времени, не cleanup.

### 3.5 Утверждённые лимиты первого закрытого среза

Это ограничения запросов почты; полная замена LoginGuard и fail2ban сюда не входит.

| Область | Предлагаемый предел |
|---|---|
| Нормализованный email, оба назначения вместе | Интервал 60 секунд; 3 новых письма за час; 5 за UTC-сутки |
| ID браузера | 10 запросов ссылок за час |
| IP / IPv6-сеть /64 | 50 запросов ссылок за час; только этот сценарий, без общего запрета входа |
| Auth-отправки платформы | 70 попыток в UTC-сутки и 2000 в UTC-месяц, с сохранением счётчиков при рестарте |
| Одновременные вызовы relay | Не более 2 для процесса; DB-захват не допускает повторного владельца одной операции |

ID браузера - серверная подписанная случайная cookie; отсутствие/очистка не обнуляет
email/IP-счётчики. IP берётся из доверенной прокси-границы, её проверяет оператор.
UA остаётся дополнительным сигналом, не идентичностью и не способом обхода лимитов.
Email-ключи счётчиков не журналируются и не хранятся как простой перебираемый hash:
для них нужен HMAC с серверным ключом и ограниченный срок хранения.

Частотные ограничения применяются одинаково к неизвестному email и всем ролям.
Лимит email подавляет доставку с единым внешним ответом, не блокирует учётку/вход.
Видимые ограничения источника и Retry-After зависят от действий источника,
не от найденной роли/существования учётки. Должны быть пределы размера таблиц,
сроки хранения и ограниченное удаление старых записей, включая неизвестные адреса.

Общий бюджет auth не доказывает остаток командной квоты Resend: перед размещением
оператор проверяет доступную квоту/другие приложения. Ошибка квоты закрывает
доставку без покупки тарифа и без непрерывных повторов. Числа выше отдельно утверждены D-064; прежний выбор Resend и правило
«5 ошибок пароля» сами по себе их не утверждали.

## 4. Следующий подшаг B - отдельное предложение после A

- Admin/owner: UV-passkey либо пароль + подтверждённый TOTP. Проверяются UV и
  сохранённое серверное основание усиленного входа, не только password-сессия.
- Недавнее подтверждение чувствительных операций, предложение срока - 5 минут;
  изменение факторов требует уже действующего усиленного доказательства.
- Одноразовые резервные коды, подтверждённое включение TOTP, зашифрованный TOTP-secret,
  защита перебора и атомарное потребление кодов. Выдача/повторная выдача не обходят step-up.
- Полный почтовый reset, обычная смена пароля, восстановление фактора и CLI строго
  разделены по принятой таблице Q2. Почта не снимает обязательный MFA и не выдаёт
  административную сессию. Если reset отозвал единственный UV-passkey, вход
  возвращается через backup/operator recovery с настройкой фактора, не через пароль.
- CLI выдаёт только короткий одноразовый enrolment-контекст, без роли/игр/admin API;
  после настройки необходим новый усиленный вход. Последний owner способен
  восстановить фактор этим путём, но правило последнего owner не ослабляется.
- Плагин two-factor Better Auth - кандидат на primitives, не объявляется готовым
  исполнением всей политики. Его реальное поведение и adapter-транзакции проверяются.

## 5. Подшаги C/D и условия рабочего включения

В C отдельно предлагаются численные параметры полной Q3 для password/passkey/MFA,
реальная внешняя неразличимость с учётом статусов/времени/бана источника, браузерный
CSP и защита форм. Существующий LoginGuard и внешний рубеж не отключаются до
проверенной согласованной замены. Общий набор ролей не меняется при регистрации:
новый пользователь получает user, active, emailVerified=false; клиент это не назначает.

В D оператор и владелец отдельно подтверждают owner/backfill 2А-02, безопасную
миграцию, защищённый вход последнего owner, работу возврата к RBAC-совместимой
версии, новые секреты/конфигурацию и доставку. До игроков нужен D-047:
резервирование с согласованным RPO и восстановление актуальной заполненной схемы.
Готовность почты этого условия не заменяет. Нельзя включить учётки на версии
«любой вошедший = owner». Рабочие данные и адреса владельцев здесь не читаются.

Новые маршруты/диспетчер A выключены по умолчанию. В A они включаются только
на закрытом стенде с искусственными данными/подменой relay. Рабочая миграция,
реальные recovery-письма и смена credentials на VPS не входят в разрешение A.
Настоящие auth-токены не должны попадать в access/error логи инфраструктуры:
проверка удаления query-параметров перед рабочим включением - задача оператора.

## 6. Области файлов A

- packages/db/src/schema.ts, новый auth-actions.ts и auth-mail.ts: действия,
  транзакции, SQL-права и постоянные mail-операции; schema exports/roles.
- Следующая свободная расширяющая миграция после 0002_user_access (предварительно
  0003_auth_mail.sql и metadata). Существующие user/saves/scores не переписывать;
  рабочую миграцию не запускать. Даты/индексы/очистка не подменяют проверки в транзакции.
- apps/hub/src/lib/auth-core.ts, auth-access.ts, новые auth-actions.ts,
  auth-mail-dispatch.ts, auth-mail-policy.ts: узкие доказательства, маршрутные
  запреты, адаптация и лимиты. Новый путь не снимает старые проверки доступа.
- apps/hub/src/instrumentation.ts: ограниченный запуск диспетчера Node;
  отключён в build/Edge и без отдельного серверного разрешения.
- Новые routes /api/account/email-confirmation/{request,consume} и
  /api/account/password-reset/{request,consume}; отдельная обработка отказа
  БД/неверного запроса без отражения email/token. Пересекающиеся Better Auth
  маршруты и server API проверяются и закрываются от обхода.
- Страницы /account/verify-email, /account/reset-password и форма запроса ссылки;
  существующий Popup используется для настоящих popup-поверхностей.
  Страницы token не кешируются, не имеют сторонних ресурсов и используют
  no-referrer. Ошибки не отражают ссылку/token/email в диагностике/HTML.
- Тесты хаба и packages/db с искусственными учётками/почтой; отчёт и промпт
  ревью после результата. Код apps/mail-relay, его профили и инфраструктура
  в A не меняются, если новая несовместимость не доказана и не согласована.

## 7. Приёмка A

1. Подтверждение и reset проходят через прежний внутренний mail-client и строгие
   v1-профили. Нельзя через body задать from, произвольный callback/URL или роль.
2. Истечение, повтор, неверное назначение/поколение/email, блокировка и смена A/B
   отвергаются. GET/предпросмотр не потребляет token; POST защищён CSRF/Origin.
3. На настоящем временном PostgreSQL: два consume; reset против CLI, смены роли,
   блокировки, смены пароля, создания passkey и сессии. Если отзыв победил,
   начатая операция не получает новое поколение. Частичная ошибка откатывает всё.
4. Старые credentials/сессии/passkey действительно не пускают после разрешённого
   reset. Подтверждение email не выпускает сессию и не повышает права.
   Admin/owner/MFA reset в A недоступен также при прямом HTTP и server API.
5. Отрицательные проверки SQL-полномочий процедуры, её назначения/цели и журнала;
   никакого общего изменения служебных полей для gf_hub. Регрессии F1-F4 сохраняются.
6. Доставка: неизменность ID/payload, два диспетчера, рестарт до/после начала HTTP,
   unknown, ошибки quota/rate/pin/secret, истёкшее действие, отзыв в гонке и лимиты.
   HTTP-ответ запроса ссылки не зависит от ожидания или результата провайдера.
7. Неизвестный email, verified/unverified, suspended и роли проверяются одинаковыми
   внешними последовательностями: body/status/Retry-After/время/контрольный запрос.
   Это не доказательство внешнего fail2ban/CSP, которые отдельно проверяются в C/D.
8. Token/пароль/payload не попадают в логи/ответы/URL возврата; читаемая БД mail-операций
   без ключа не выдаёт plaintext token. Пропажа ключа не даёт незашифрованного fallback.
9. Ключевые негативные проверки должны краснеть при снятии защиты во временной
   копии. При реализации выбираются реальные критические проверки, не тесты,
   повторяющие текст исходника. Browser/Next сборка и полный CI остаются отдельными
   проверками; локальные результаты не выдаются за проверку рабочей среды.

Проверки выполняются на искусственных данных, без настоящего ключа Resend и
рабочей БД. Если команда включает Git, на неё требуется отдельное разрешение.
После A показать проверяемый результат и подготовить точный патч/manifest для
ревью. Самостоятельно не запускать проверяющего, Git, публикацию или мониторинг.

## 8. Что предлагается утвердить сейчас

Только подшаг A в описанном закрытом объёме; предложенные сроки и mail-лимиты;
небольшую постоянную таблицу подготовленных auth-отправок с диспетчером внутри
хаба и отдельным файловым ключом шифрования payload. Инфраструктурный ключ сейчас
не создаётся; его подготовка отдельно перед размещением.

Не предлагается сейчас утверждать все численные параметры Q3, реализацию B/C/D,
список настоящих owner, регистрацию, рабочие миграции, Git или публикацию.
