## Совместимость с gf-update: применять только вместе

На сервере используются root-копии compose.yml и будущей compose.mail.yml.
В root .env при согласованном включении добавляются строки подготовленного файла
параметров: COMPOSE_FILE=compose.yml:compose.mail.yml, настоящий image по digest и
имя подготовленной egress-сети. Сначала должны быть готовы все значения, сети и
секреты; пустой image/network намеренно останавливает Compose.

Это нужно **всем** последующим вызовам Compose, включая gf-update. Если запускать
старую конфигурацию без overlay, `--remove-orphans` может удалить mail-relay,
а пересоздание hub потеряет почтовые параметры. Не подключать overlay только
разовым `-f`, оставляя таймер на другом наборе файлов. Перед включением отдельно
согласовать остановку/возобновление таймера и сохранение предыдущего root-конфига.

gf-update не включает mail-relay в явный список pull. Однако `config --images hub`
включает образы зависимостей: на локальном Compose 5.6.0 подтверждено, что текущая
функция image_ids передаёт несколько строк одним аргументом image inspect и получает
запасное «нет:…». По отдельному «да» владельца deploy/update.sh исправлен локально:
выбирается services[имя].image из JSON. Проверка извлечённой текущей функции — 1/1;
image inspect подменён, Engine не используется. Root-копия updater не менялась.
До включения требуется проверить целевой Compose и наличие python3 на VPS.
Шлюз закреплён digest и обновляется отдельным явным действием.
Зависимость hub от mail-relay сохраняется в объединённой конфигурации. При будущем
откате меняются согласованно оба файла/параметры; существующие секреты не удаляются.

Даже после исправления селектора неизменные образы позволяют обычному gf-update
выйти до применения нового конфига. Первоначальное включение требует отдельно
согласованного --force либо явного up с полным набором файлов/параметров.
Ни один из этих запусков здесь не выполнялся. Подробности и отдельный патч —
[перепроверка размещения](HUB-MAIL-DEPLOYMENT-RECHECK.md).

## Команды сохранения секретов — подготовлены, ещё не выполнялись

Следующий отдельно разрешаемый шаг. **VPS хаба, root, Bash**, в интерактивном
терминале; не запускать блок в fish. Значение вводится на запрос, не в команду,
не в чат и не в .env. Каталог root 0700 закрывает файлы на хосте; 0644 у самих
файлов нужны для bind-mount Compose и чтения uid 1000 (П-044). Уже существующие
файлы блок не перезаписывает: ротация — отдельная операция.

~~~bash
(
  set +x
  set -euo pipefail
  [[ $EUID -eq 0 ]] || { printf 'Нужен root\n' >&2; exit 1; }
  cd /etc/docker/containers/game-factory
  [[ ! -L secrets ]] || { printf 'Каталог secrets не должен быть ссылкой\n' >&2; exit 1; }
  if [[ ! -e secrets ]]; then install -d -m 0700 secrets; fi
  [[ -d secrets && $(stat -c '%u:%a' secrets) == 0:700 ]] || {
    printf 'Нужен каталог secrets с владельцем root и правами 0700\n' >&2; exit 1;
  }
  for GF_MAIL_FILE in secrets/mail_service_secret secrets/resend_api_key; do
    [[ ! -e $GF_MAIL_FILE && ! -L $GF_MAIL_FILE ]] || {
      printf 'Почтовый секрет уже существует; перезапись запрещена\n' >&2; exit 1;
    }
  done
  command -v openssl >/dev/null
  umask 077
  IFS= read -r -s -p 'Resend Sending access API key: ' GF_MAIL_RESEND_KEY </dev/tty
  printf '\n' >/dev/tty
  [[ $GF_MAIL_RESEND_KEY =~ ^re_[A-Za-z0-9_-]{16,256}$ ]] || {
    unset GF_MAIL_RESEND_KEY; printf 'Неверный формат API-ключа\n' >&2; exit 1;
  }
  GF_MAIL_SERVICE_KEY=$(openssl rand -hex 32)
  [[ $GF_MAIL_SERVICE_KEY =~ ^[0-9a-f]{64}$ ]]
  GF_MAIL_CREATED=()
  trap 'GF_MAIL_RC=$?; unset GF_MAIL_RESEND_KEY GF_MAIL_SERVICE_KEY; if (( GF_MAIL_RC != 0 )); then for GF_MAIL_FILE in "${GF_MAIL_CREATED[@]}"; do rm -f -- "$GF_MAIL_FILE"; done; fi; exit "$GF_MAIL_RC"' EXIT
  trap 'exit 130' INT
  trap 'exit 143' TERM
  set -o noclobber
  exec {GF_MAIL_FD}>secrets/resend_api_key
  GF_MAIL_CREATED+=(secrets/resend_api_key)
  printf '%s' "$GF_MAIL_RESEND_KEY" >&"$GF_MAIL_FD"
  exec {GF_MAIL_FD}>&-
  exec {GF_MAIL_FD}>secrets/mail_service_secret
  GF_MAIL_CREATED+=(secrets/mail_service_secret)
  printf '%s' "$GF_MAIL_SERVICE_KEY" >&"$GF_MAIL_FD"
  exec {GF_MAIL_FD}>&-
  unset GF_MAIL_RESEND_KEY GF_MAIL_SERVICE_KEY
  chmod 0644 secrets/resend_api_key secrets/mail_service_secret
  printf 'Созданы два почтовых секрета; содержимое не выводится\n'
)
~~~

Блок без изменений испытан через PTY в изолированном Linux user namespace:
root только внутри namespace, искусственные файлы, сеть отключена. **17/17**:
ввод/trace, существующие файлы и ссылки, права, ошибки открытия/записи/chmod,
сигналы и cleanup. Три мутации в тестовых копиях дали ожидаемые красные результаты.
Настоящий root-каталог VPS и чтение uid 1000 в контейнере не испытывались.
Он не запускает контейнеры и не отправляет письмо.

Подтверждено ограничение cleanup: сигнал между созданием любого файла и добавлением
его пути в GF_MAIL_CREATED оставляет пустой файл 0600. Секрет в этом сценарии не
сохраняется; следующий запуск откажет. После прерывания оператор должен проверить
состояние файлов, а не удалять их вслепую. Автоматическое удаление такого остатка
и изменение Bash-блока в этот подшаг не включены.

не затронуты. После согласования применяются только root-копии, не файлы рабочей
