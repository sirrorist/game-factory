# План образа mail-relay

2026-10-22. Подготовлен по «Делай» в ответ на предложение подготовить план.
Статус: реализация утверждена владельцем («да»); конфигурация и проверки
подготовлены локально. [Результаты и ограничения](HUB-MAIL-IMAGE-REPORT.md).
Сборка, публикация, Git-операции и изменение root-конфигурации этим документом
не разрешаются. Каждый такой переход согласуется отдельно после показа результата.

## Результат

Отдельный образ ghcr.io/sirrorist/game-factory-mail-relay для linux/amd64,
связанный с конкретным прошедшим CI коммитом. После публикации его digest
передаётся оператору для GF_MAIL_RELAY_IMAGE. Установка образа, запуск шлюза,
проверки сетей и настоящее письмо остаются следующим согласуемым шагом.

## Исходное состояние до реализации

- [Dockerfile шлюза](../apps/mail-relay/Dockerfile) уже существует: обязательный
  NODE_IMAGE, только корневой package.json и src шлюза, USER node, без npm install.
- [Корневой Dockerfile](../Dockerfile) не содержит target mail-relay.
  [Publish](../.github/workflows/publish.yml) собирает hub/play/games/migrate
  через target корневого Dockerfile, привязывая исходники к SHA события.
- [CI](../.github/workflows/ci.yml) не испытывает контейнер шлюза.
  [Docker workflow](../.github/workflows/docker.yml) не отслеживает его src/Dockerfile.
- main.ts слушает порт 4102, без обязательной конфигурации завершает запуск
  с ошибкой; реальные ключи для сборки не нужны. Это вывод чтения, не smoke образа.
- gf-update не управляет отдельным обновлением закреплённого образа шлюза.
  Его согласованный локальный патч выбора образов не изменяет эту границу.

## Предлагаемая реализация

1. **Закрепить базу и ограничить контекст.** Проверить официальный образ Node 22,
   совместимый с проектом (Node >= 22.18, прямой запуск .ts), выбрать конкретный
   patch и digest с linux/amd64. Зафиксировать выбранную базу литералом FROM
   вместо свободного NODE_IMAGE. Конкретную версию/digest подтвердить при реализации,
   не подставлять вымышленное значение и не объявлять прежний тег актуальным.
   Добавить Dockerfile.dockerignore только для шлюза: в контекст допускаются
   Dockerfile, корневой package.json и apps/mail-relay/src. Корневые Dockerfile и
   .dockerignore, зависимости и образы других сервисов не менять.

2. **Проверять образ до разрешения публикации.** В CI добавить отдельную задачу
   mail-image с contents: read, без packages: write и без ключа Resend.
   Собирать через apps/mail-relay/Dockerfile. Испытывать полученный локальный образ
   в контейнере с --network none, read-only, uid 1000, cap-drop ALL и no-new-privileges:
   отсутствие/пустые файлы конфигурации и неверный pin дают отказ; искусственная
   корректная конфигурация запускается; локальный HTTP-запрос без авторизации
   получает отказ. Порт на хост не публиковать, обращаться внутри контейнера.
   Ожидание старта ограничено общим сроком, контейнеры удаляются в cleanup.
   Положительный сценарий и отказ при отсутствии конфигурации обязательны:
   иначе неработающий образ может выдать ложный успех негативной проверки.
   Сверить User/Cmd/образ базы, отсутствие посторонних файлов и node_modules.
   Искусственные секреты монтировать только во время smoke, не передавать в build.

3. **Добавить отдельную задачу в Publish.** Существующую матрицу четырёх сервисов
   сохранить. Новый job собирает отдельный Dockerfile, публикует только
   game-factory-mail-relay:<полный SHA> и выдаёт digest/платформу/revision в summary.
   Автоматический запуск — после успешного CI от push в main, checkout строго
   workflow_run.head_sha. Весь CI, включая mail-image, должен завершиться успешно.
   Для ручного запуска требовать main и подтверждённый успешный CI для того же SHA;
   при отсутствии такого результата — отказ. Чтение CI через actions: read,
   публикация через штатный GITHUB_TOKEN/packages: write, без нового PAT.
   Не разрешать входной произвольный ref/Dockerfile/base и публикацию из PR/форка.
   Для нового образа не вводить :main/:latest: оператор использует digest.
   После ревью отдельно согласовано: оба режима используют последний push-CI SHA;
   автоматическое событие должно соответствовать этому run. При новом красном или
   незавершённом run публикация запрещена. Формы path — ci.yml и ci.yml@main.

4. **Проверить изменения локально и подготовить ревью.** Проверить YAML, точный SHA
   checkout, условия публикации и отсутствие дополнительных прав/секретов.
   Негативные проверки должны обнаруживать снятие ограничений main/успешного CI/
   совпадения SHA, подмену Dockerfile и незакреплённую базу. Сборку и smoke выполнять
   только после отдельного согласия; если Engine недоступен, честно оставить их
   непроверенными до CI. Предоставить владельцу точный патч, результаты и промпт.
   Ревьюера запускает владелец. Это не повторное полное ревью транспорта/auth.

5. **Публиковать только после отдельного разрешения.** После приёмки показать
   изменения и отдельно согласовать конкретные Git-операции: dev и main независимо.
   Запуск Publish также согласовать отдельно; успешный CI сам по себе разрешением
   не служит. После публикации записать SHA, digest, платформу и использованную базу.
   По умолчанию сделать одну проверку статуса и завершить ход; если образ ещё
   собирается, сообщить оставшийся внешний этап без мониторинга и повторных опросов.

## Границы приёмки

| Результат | Чем подтверждается |
|---|---|
| Образ запускается на совместимом Node | Сборка, metadata и положительный smoke |
| Без конфигурации не работает | Отрицательные smoke на том же образе |
| Ключи/данные не входят в сборку | Ограниченный контекст и проверка состава образа |
| Публикуется проверенный коммит | CI-gate, checkout точного SHA, отрицательные проверки |
| Размещение использует нужный артефакт | GHCR digest + revision + linux/amd64 после публикации |

Smoke без сети не доказывает egress, доступность Resend, доставку и фактическую
изоляцию VPS. Настройка tracking, остаток квоты, чтение файлов uid 1000,
root-копии, применение overlay и получатель тестового письма остаются условиями
[плана размещения](HUB-MAIL-DEPLOYMENT.md). Auth callbacks не подключаются.

Далее владелец оценивает результат и запускает ревью по
[готовому промпту](HUB-MAIL-IMAGE-REVIEW-PROMPT.md). Локальная сборка, Git,
публикация и изменение root-копий по-прежнему требуют отдельных разрешений.
