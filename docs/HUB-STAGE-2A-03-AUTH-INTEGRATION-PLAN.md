## 2. Предлагаемый стенд

Отдельный job auth-a-integration в существующем ci.yml, на одноразовом runner,
с permissions contents: read, без packages/actions write и настоящих secrets.
Своя service-БД Postgres с тем же закреплённым образом, что у существующего check.
Миграции 0000–0003 выполняются только в этой новой БД; Next подключается как gf_hub.
Искусственные user/developer/admin/owner и guard обязательного фактора — fixtures,
а не регистрация/настройка настоящего MFA. Все временные ключи/пароли создаёт harness: файлы 0600 внутри каталога 0700,
удаление при штатном завершении и ошибке. URL владельца тестовой БД не передаётся Next.

Путь запроса:

1. Chromium → https://localhost:TEST_TLS_PORT → локальный HTTPS-прокси harness.
2. Прокси → standalone Node Next на 127.0.0.1:TEST_NEXT_PORT.
3. Next → неизменённый http://mail-relay:4102/v1/send → тестовый collector.
4. Next и управляющий harness используют разные соединения тестовой БД.

Для runner добавить mail-relay → 127.0.0.1 в его hosts только на время job.
Collector слушает loopback:4102; если порт занят, setup падает, не выбирает внешний
адрес и не меняет клиент. Это конфигурация одноразового CI runner, не VPS.
Collector реализует v1 envelope, проверяет синтетический service-secret, метод/path,
ограничивает вход и число сохранённых сообщений (не более 100). Управление исходами — из памяти
родительского test harness; не добавлять debug/admin endpoints в хаб.

TLS-прокси использует временный self-signed сертификат localhost, созданный в job.
Chromium принимает только этот тестовый setup через ignoreHTTPSErrors; запреты
Origin/CSRF, Secure/__Host cookies и browser security не отключаются.
Host/Origin/X-Forwarded-Proto согласованы с внешним HTTPS origin хаба.
Это не проверка публичной TLS-цепочки, Traefik или сетей VPS.

В окружении Next только явно необходимые переменные. Не наследовать GF_* и
ключи произвольной машины; не передавать GITHUB_TOKEN/Resend credentials.
Collector не обращается к Resend и не запускает настоящий relay/provider.
Минимальный пустой реестр/каталог — fixture через формат packages/registry:
новый job не собирает игры и не делает check-prod.

## 3. Сборка и запуск

- Одна production standalone-сборка, без next dev. При сборке обе новые auth-метки
  намеренно выставлены closed-test, но DB/auth/mail ключи и runtime origin отсутствуют.
  Сборка обязана завершиться без создания mail-операций/попыток доставки.
  Это проверяет защиту build-phase, а не только наличие условия в исходнике.
- Подготовить из результата временный layout вне checkout как у Dockerfile: standalone,
  apps/hub/.next/static, apps/hub/public. Старт только из этой копии; доступность
  рабочего source tree не должна маскировать недостающие runtime-файлы: cwd — этот
  layout, NODE_PATH не наследуется, ссылки за пределы layout отвергаются.
  Дочерний Node запускается с permission model и allow-fs-read только для layout
  и искусственных runtime-данных/ключей. Checkout не включён в разрешения;
  child process, worker и native addons не разрешаются. Тест с намеренной
  абсолютной файловой зависимостью вне layout обязан получить ERR_ACCESS_DENIED;
  без ограничения тот же контроль обязан успешно прочитать искусственный файл.
  Ограничение не объявляется песочницей недоверенного кода: здесь оно выявляет
  случайную runtime-зависимость доверенного standalone от исходников.
- Все режимы ниже используют тот же build; runtime-флаги не должны застыть в bundle.
- Старт через обычный server.js, без ручного вызова register/startAuthMailDispatcher
  из теста. Готовность — HTTP, затем проверка реальных SSR-форм и локальной доставки.

Матрица runtime:

| API-флаг | Dispatcher-флаг | Ожидание |
|---|---|---|
| Нет | Нет | Обе страницы/API закрыты, pending остаётся pending, collector пуст |
| Нет | closed-test | То же; одна dispatcher-метка не включает A |
| closed-test | Нет | Формы/API доступны, запрос сохраняется, отправки нет |
| closed-test | closed-test | Pending обрабатывается без предварительного auth-запроса |
| Оба включены, mail-key отсутствует/неверной длины | Оба включены | Старт не достигает готовности; нет fallback/письма |

В выключенных режимах mail-key может указывать на заведомо отсутствующий тестовый
файл: сервер должен оставаться работоспособным без его чтения. Обычный auth-secret
для сессий и конфигурация тестовой БД готовятся независимо от mail-key.

## 4. Браузерные сценарии

1. Обе страницы без token отдают SSR-формы запроса с email и подписанным намерением;
   после hydration обычный submit проходит весь путь через instrumentation и collector.
   Ответ запроса ссылки приходит, пока collector удерживает результат доставки.
   Один и тот же submit/повтор ответа сохраняет логическое намерение; новое явное
   действие создаёт новое. Для положительных доставок использовать свежие fixtures,
   не ждать минутами cooldown и не ослаблять лимиты приложения.
2. Verify: получить ссылку из collector в памяти, открыть/reload/загрузить через
   HTTP preview. До явного POST emailVerified/consumedAt не меняются. Кнопка
   подтверждает адрес; повтор отвергается; сессия и новые права не выдаются.
3. Reset: ввести новый пароль в настоящей форме, подтвердить. Новый пароль принимает
   обычный вход, старый — нет; старые сессии/passkey отозваны. emailVerified и данные
   игр не меняются. После успеха нет автоматического входа/смены учётки.
4. Войти как B и открыть ссылку A: conflict в UI, ни одна учётка не переключается,
   A-token не потребляется. В чистом browser context ссылка A остаётся применимой.
5. Просроченные/отозванные ссылки, admin/owner и обязательный guard reset не обходят.
   Для проверки expiry допустимо менять только timestamps тестовой fixture в БД.
   Unknown email/запрещённая учётка получают тот же ответ запроса ссылки; collector
   не получает письмо. Это не доказательство полной временной неразличимости Q3.
6. Прямые POST через Playwright APIRequestContext: чужой/отсутствующий Origin,
   отсутствующий/неверный CSRF. Получить реальный отказ proxy/handler и отсутствие
   изменений БД. Не подменять эту проверку одним CORS-отказом браузера.
7. Штатные Better Auth verify/reset/send GET/POST остаются закрыты в собранном хабе;
   регистрация по-прежнему закрыта. Старые тесты этих границ сохраняются.
8. На настоящих HTTP-ответах обеих token-страниц — no-referrer/no-store/noindex.
   Собирать Referer для ранних автоматических запросов CSS/JS/fonts и fetch:
   bearer не появляется ни в одном заголовке. Автоматические ресурсы — только
   свои. Отдельный намеренный probe к локальному другому HTTPS origin также
   не получает Referer; это collector harness, не внешний интернет.
   Метатег не должен маскировать неправильный HTTP Referrer-Policy.
   У запросов документа и probe Referer отсутствует. У шрифта, объявленного во
   внешнем CSS, допустим точный безопасный URL этого реально загруженного stylesheet;
   соответствие шрифт→stylesheet проверяется по CSSOM. Во всех наблюдениях запрещены
   bearer и URL token-страниц. Production-заголовки ради стенда не меняются.
   Для каждого сценария — свежий context, наблюдение до navigation, уникальные
   probe URL без кеша. Обязательны успешные CSS/JS/font-запросы и cross-origin
   probe на стороне HTTPS-сборщика. Контрольная страница с unsafe-url обязана
   дать наблюдаемый Referer без bearer; непоступивший запрос — ошибка проверки.

Fixtures разделены по сценариям, общие почтовые бюджеты не превышаются. Точное
число тестов фиксируется после реализации; не объявлять заранее выдуманный pass.

## 5. Диспетчер в собранном процессе

- Pending подготовлен harness до старта. С включёнными флагами поступает ровно один
  вызов collector без запроса пользователя к auth API: доказательство autoload
  instrumentation в собранном сервере. В выключенных режимах вызовов нет.
- Несколько pending: наблюдать фактическую параллельность collector, максимум два
  для одного запуска Node: collector удерживает первые два ответа, третьего вызова
  до их освобождения нет. DB-захват/предварительное сохранение дополнительно
  сверяются другим соединением с аргументом HTTP, а не вызовом внутренней функции.
- Accepted/not_accepted/unknown от collector корректно завершают операцию;
  произвольная ошибка/оборванный ответ не запускают второй HTTP для той же операции.
- Restart до начала отправки: первый процесс с dispatcher выключен сохраняет
  pending, останавливается; второй с dispatcher включён использует тот же ID/createdAt.
- Crash после начала: collector уже принял запрос и удерживает ответ, БД показывает
  committed started. Убить только дочерний Next через SIGKILL; перезапустить.
  Для детерминированной проверки cleanup разрешено состарить startedAt тестовой
  строки в БД, без 60-секундного ожидания. Итог unknown, collector не видит повтор.
- SIGTERM во время запроса отменяет работу и завершает процесс за заданный предел.
  Если результат не успел сохраниться, started трактуется как неизвестный при
  восстановлении, не как разрешение нового письма. Проверяется отсутствие новых
  захватов после начала остановки; cleanup harness обязателен и при падении теста.

Не раскрывать новые публичные диагностические маршруты и не вызывать register
вручную ради зелёного результата. Если тест выявляет несовместимость текущего
runtime-кода с Next, показать её отдельно с минимальным планом исправления;
не переписывать auth/adapter/транспорт внутри реализации тестового стенда.

## 6. Ограничения, файлы и порядок выполнения

Предлагаемые пределы: job 20 минут, build 8 минут, readiness процесса 30 секунд,
обычный case 20 секунд, restart/crash case 30 секунд, shutdown 10 секунд.
Перед setup все адреса проверяются как loopback/тестовый CI service; ошибки
настройки не засчитываются как ожидаемый отказ безопасности. После SIGKILL/timeout
не оставлять браузер, серверы, клиентов БД, открытые порты и временные ключи.
Короткие ожидания внутри ограниченного теста не превращаются в мониторинг CI.
Группа процесса отслеживается после выхода лидера: ограниченный TERM, затем KILL
и проверка отсутствия исполняющихся участников. Retirement запрещает повторные
сигналы после наблюдённого исчезновения группы. Он не удостоверяет принадлежность
группы, если числовой PGID был переиспользован между наблюдениями; более сильная
гарантия стабильного владения группой в этом стенде не реализована. Ошибки abort учитываются итоговым
cleanup, остальные ресурсы очищаются и после ошибки одной задачи. Осиротевшие
зомби не исполняются и не держат порт; их сбор остаётся за init одноразового runner.

Предлагаемые области:

- .github/workflows/ci.yml: новый отдельный job; прежние check/mail-image не менять.
- package.json: явная команда test:auth-integration; общий pnpm test не должен
  самостоятельно запускать build/браузер/standalone-стенд.
- tests/auth-a/: harness, HTTPS-прокси, collector, integration-сценарии с расширением
  .integration.ts, чтобы прежние *.test.ts/e2e-glob не запускали их повторно.
- packages/db/test/: отдельные test-only fixtures/счётчики наблюдений при необходимости;
  никакой записи реальных учёток и никаких новых web API для fixtures.
- Типы тестов/CI, локальные unit-проверки harness и адресные мутации защит.
  Новых npm-зависимостей не предлагается: Node, Playwright и текущий DB-пакет.
- Отчёт, точный патч/manifest без Git и промпт ревью. Рабочие Dockerfile/compose,
  роли/миграции/профили relay и настоящие секреты не входят в изменение.

Последовательность разрешений:

1. Объём и два уточнения ревью утверждены владельцем: «делай».
2. После согласия — реализовать CI/harness/tests, локально проверить типы и лёгкие
   тесты harness, подготовить конкретный результат и промпт ревью владельцу.
   По D-049 не выполнять локально next build/Chromium без отдельного разрешения.
3. Отдельно согласовать состав для Git: A зависит от ещё не опубликованного 2А-02.
   Нельзя отправить новые тесты поверх одного почтового коммита без этой зависимости.
   Commit/push dev и разрешённый CI-запуск — следующий отдельный шаг; main/образы/прод
   не входят в него. Текущий план не разрешает ни одной Git-команды.
4. На внешнем CI по умолчанию одна проверка статуса, без watch/sleep/фоновых опросов.
   Фактический результат сообщить отдельно; отсутствие результата не считать успехом.

Job не использует deploy/root-копии/ключи Resend и не публикует образы. Артефакты —
ограниченный санитизированный TAP/JSON с результатами и ошибками setup. Не загружать
.env, ключи, cookies, полные mail-body/HTML, HAR/trace или token-ссылки; сравнения
делать без печати исходных значений, включая ошибки assert. Сырые stdout/stderr
дочернего процесса не приклеивать автоматически к публичной ошибке теста.

## 7. Приёмка и границы результата

Готовность стенда: точный состав, зелёные локальные лёгкие проверки и ревью без
блокирующих находок. Это ещё не запуск интеграционных тестов.
Готовность проверки A: зелёный job на согласованном точном SHA с production standalone,
настоящими PG/Chromium, SSR+hydration, proxy/куками/headers и реальным autoload dispatcher.
Негативные сценарии обязаны падать при адресном снятии соответствующей защиты;
полный набор bundle/browser мутаций выполняется только в разрешённом CI.

Не доказываются: Docker runtime/ресурсные лимиты образа, публичный TLS/DNS,
аппаратный WebAuthn, реальные почтовые учётки/доставка, инфраструктурные логи,
ротация ключей, рабочие миграция/backfill/бэкап. B/C/D и D-047 остаются отдельными
условиями; успешная проверка A не включает регистрацию и не закрывает этап 2А.
