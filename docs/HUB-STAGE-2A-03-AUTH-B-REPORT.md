# Закрытый B: серверный срез, 2026-11-05

Статус: локальная реализация начата по D-066; **B не готов и не подключён**.
[Принятый план R3](HUB-STAGE-2A-03-AUTH-B-PLAN.md) прошёл ревью требований.
Ревью плана не является ревью этого кода. Git, публикация и рабочее применение
не выполнялись. Подагенты и внешние ревью самостоятельно не запускались.

## Что подготовлено

- Закрытая схема auth_private: TOTP/UV-факторы, proof, контексты, резервные
  хеши, резервации попыток и постоянные раздельные счётчики. Миграция 0004
  расширяет схему; public saves/scores и список public-таблиц не меняются.
- Убран blanket GRANT. gf_hub получает явные public-права и только колонки
  expires_at/updated_at для refresh session. Снимаются старые column grants,
  лишнее членство и запись в закрытую схему. Новая gf_auth — только LOGIN
  и перечисленные EXECUTE; нет прямого чтения/DML auth_private.
  Повторная выдача не принимает владение постоянными объектами; временные таблицы
  разрешены и не считаются таким владением. Реальные роли не изменялись.
- Короткие SQL-процедуры: снимки до crypto, атомарная committed-резервация до
  verifier, сравнение generation/credential/factor/step при завершении,
  session+proof в одной транзакции, отзыв и ограниченная настройка.
- Proof связывается с исходным bearer и идентификатором выпуска; UPDATE token/id/
  user/generation/created_at запрещён в SQL. Удаление session уносит proof по FK;
  повторная вставка не возвращает его. Истёкшую session нельзя продлить UPDATE.
- Активный фактор сам требует усиления, даже если guard-маркер отсутствует;
  SQL password-only выпуск такого пользователя отвергается.
- CSPRNG 32-байтные контексты; резервные коды — 10 независимых 128-битных значений.
  В БД их доменные SHA-256-хеши; пароль остаётся salted scrypt. TOTP проверяется
  на Node HMAC, секрет шифруется AES-GCM с привязкой user/factor/key-id и отдельным
  key-ring. Неверный ключ/тег/привязка не дают plaintext-fallback.
- Отдельные Node-контроллер и HTTP-модуль: пароль → pre-auth → TOTP, настройка,
  резервное восстановление, смена пароля и повторный выпуск кодов. Cookie
  подписывается совместимо с Better Auth; читается и проверяется исходная cookie.
  POST/Origin/CSRF, строгие поля, ограниченное чтение, no-store/no-referrer.
  Эти модули **не зарегистрированы в маршрутах Next**.
- Коды возвращаются после успешного создания набора один раз; повтор завершения
  отвергается. BACKUP_WARNING рекомендует бумагу/офлайн-хранение и объясняет
  полномочия кода. Интерфейс показа и предупреждения ещё предстоит подключить.
- Backup-восстановление отзывает весь старый набор, TOTP/passkey и session;
  старый пароль отключается. Для TOTP требуется задать новый пароль; UV-настройка
  сможет обеспечить вход без него. Операторская процедура требует новый пароль,
  но действующий CLI ещё не переключён на неё.

Новые native-проверки используют разные backend, настоящий gf_hub и gf_auth;
проверяют SET ROLE/DML/EXECUTE после повторной выдачи прав, видимость committed
резервации до verifier, шестой правильный код вне бюджета, один результат TOTP,
свою настоящую подписанную cookie attacker, отзыв между crypto и записью,
два разных backup-кода одного набора. Кластеры завершены штатным cleanup.

HTTP-проверки включают реальный LoginGuard: после неверных backup-кодов правильный
пароль+TOTP проходит за общим IP и IPv6 /64; отдельный источник сохранён.
Мутация backup→парольный LoginGuard краснит именно этот успешный вход.
Другие мутации: replay TOTP, старое поколение, изменённый ciphertext фактора,
отсутствие сохранённой резервации, отсутствие FK/cascade proof, неверная AAD-привязка,
постоянный bearer вместо CSPRNG и отключение Origin/CSRF.

Временный native PG распакован из официальных пакетов PostgreSQL/Debian с SHA-256
из их HTTPS-индексов; системная установка не выполнялась. В репозиторий бинарники
не добавлены. Sandbox сначала запретил initdb; успешный прогон выполнен после
разрешения локального теста вне sandbox. Это не состояние рабочего сервера.
Полный DB suite сначала выявил два отказа из-за временной таблицы старого F4-теста;
после исправления проверки постоянного владения все 101 сценарий прошли. Затем
добавлена проверка активного фактора без guard; итоговый повтор — 102/102.

Для чистого unit-снимка потребовалось включить весь неизменённый локальный контекст
2А-02/A/mail, не только старые tracked-файлы этой рабочей копии. Первые неполные
снимки дали ошибки отсутствующих исходников/compose-примера; после их добавления
выполнен полный прогон 326/326. Посторонний старый untracked промпт исключён;
никакой красный сценарий изменения B не отключался. Снимок не является новым
Git-коммитом или доказательством состава отдельной dev-ветки.
