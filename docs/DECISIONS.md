# Журнал решений

Формат: **что решили** → почему → что отвергли. Отменённое не удаляется, а помечается
"заменено D-0xx". Источник: `владелец` - решил человек; `агент` - предложил агент,
владелец принял или не возражал.

## 2026-09-25 - сессия планирования и скелет MVP

**D-001. Основной язык - TypeScript; другие языки - через WASM и контейнеры.** (владелец)
Один язык для хаба, игр, SDK и ИИ-агента; у ИИ по TS больше всего обучающих примеров.
Другие языки: клиент игры - Rust/C/C++/Go/C# через WASM или готовый экспорт движка
(поле `toolchain`); бэкенд игры - любой язык в контейнере (этап 3).

**D-002. Монорепо: pnpm workspaces; Turborepo - когда появятся тяжёлые сборки.** (агент)
Пока задач немного и они быстрые - хватает скриптов pnpm. Turborepo добавим вместе с
Next.js и Vite (этап 0б), когда кеш сборок начнёт окупаться.

**D-003. Хаб и админка - Next.js + shadcn/ui.** (владелец)

**D-004. Сборка игр - Vite.** (владелец)

**D-005. Движки: Phaser 4 (2D), PixiJS v8 (2D-рендер), Three.js (3D), Rapier (физика), Howler.js (звук).** (агент, владелец доверил выбор)
Phaser - движок целиком, быстрый старт. Pixi - когда нужна своя архитектура. Three -
стандарт 3D в вебе. Rapier - WASM, детерминированная, 2D и 3D. Отвергнуто: Babylon.js
как дефолт (тяжелее, для "движка целиком" в 3D - позже, если понадобится).

**D-006. Очередь задач - BullMQ на Valkey, за своим интерфейсом `JobQueue`.** (агент, владелец спросил про RabbitMQ)
Задачи (сборка, превью, ИИ-агент) - это "задание с повторами, таймаутом и прогрессом",
ровно то, что делает BullMQ. Valkey всё равно нужен для лидербордов, лишнего сервиса нет.
RabbitMQ отвергнут: брокер для обмена событиями между многими сервисами на разных
языках - у нас воркеры на TS, а бэкенды игр в очередь не ходят. Если понадобится
шина событий между языками - NATS (легче RabbitMQ).

**D-007. Файлы - S3: MinIO локально, свой S3 по профилю хранилища.** (владелец)
Профили хранилищ в админке: endpoint, регион, бакет, ключи; игре можно назначить профиль.
Ключи в БД - зашифрованы мастер-ключом из файла с правами `600`, ввод - скрытым полем,
после сохранения видно только "задан, длина N".

**D-008. Игра = пакет с манифестом `game.json`.** (агент)
Хаб не зависит от того, чем игра собрана. Манифест строгий: неизвестные поля - ошибка.

**D-009. Домены: хаб `games.youranus.ru`, игры `<id>.play.youranus.ru`.** (владелец + агент)
Владелец хотел `*-play.youranus.ru` - так нельзя: wildcard в DNS и сертификатах бывает
только на целую левую метку (`*.что-то`). Поэтому `*.play.youranus.ru`. Сертификат -
бесплатный wildcard Let's Encrypt через DNS-01; нужен API DNS-провайдера для автопродления.

**D-010. До открытия платформы игры живут на поддомене того же домена; перед открытием - отдельный домен.** (владелец)
Цена компромисса: хаб и игры - "один сайт" для браузера (same-site), SameSite-cookies не
защищают хаб от CSRF со стороны игр; игры могут ставить cookies на `youranus.ru`.
Меры сейчас: кука хаба с префиксом `__Host-`, CSRF-токены и проверка `Origin`. Перед этапом 5
владелец покупает отдельный домен для игр и вносит его в Public Suffix List.

**D-011. Пока всё на одном VPS; разделение "доверенная / грязная" машина - перед открытием.** (владелец)

**D-012. Офлайн-архив - сейчас только для статических игр.** (владелец)
Простые игры на HTML/CSS/JS скачиваются сразу. Игры с бэкендом, S3 и т. п. - отдельный
разговор (этап 3: `docker-compose.yml` + статика).

**D-013. Ядро - без npm-зависимостей.** (агент)
play-server, CLI, манифест, реестр, SDK, мост - только стандартная библиотека Node.
Почему: play-server стоит на "грязной" стороне, каждая зависимость - поверхность атаки и
цепочка поставок; ядро мелкое и хорошо тестируется. Вынужденная причина в этой сессии -
реестр npm был закрыт, но решение осталось бы и без неё. Отвергнуто: zod в ядре (zod будет
в хабе для API), fflate/yazl для записи zip (запись - 100 строк; **чтение** чужих архивов
на этапе 2 пойдёт через проверенную библиотеку - там самописный парсер опасен).

**D-014. SDK - классический скрипт с JSDoc-типами, а не ES-модуль.** (агент)
Модульные скрипты не грузятся через `file://`, а офлайн-архив открывается именно так.
Один исходник работает везде: `<script src="gf-sdk.js">` в статике, `import '@gf/game-sdk'`
в Vite (обёртка `index.js`). Типы - `index.d.ts`, проверка - `tsc --checkJs`.

**D-015. Опубликованная версия неизменяема.** (агент, владелец принял правила песочницы)
Та же `version` с другим содержимым - отказ сборки. Откат - переключение указателя
на прошлую версию. `--replace` - только для локальной отладки.

**D-016. TypeScript исполняется Node напрямую (type stripping), без сборки.** (агент)
Node ≥ 22.18. Ограничения - только стираемый синтаксис, импорты с `.ts`. Отвергнуто:
tsx/ts-node (лишние зависимости), сборка ядра в JS (лишний шаг и рассинхрон).

**D-017. CI/CD - GitHub Actions; деплоя на VPS пока нет.** (владелец) - *деплой: заменено D-033*
Владелец запускает сессии агентов на том же VPS; деплой - отдельное решение позже.
CI: типы, юнит, сборка игр, офлайн-архивы (артефакт workflow), e2e в Chromium.

**D-018. Service Worker на поддоменах игр запрещён (этап 0).** (агент)
SW переживает смену и даже снятие версии игры и продолжает отдавать старое содержимое
со своего origin. play-server отвечает 403 на запрос скрипта SW (`Service-Worker: script`).
Пересмотреть, если появится игра, которой нужен офлайн-кеш в браузере.

**D-019. Тесты - `node:test` + Playwright как библиотека, без тест-раннеров.** (агент)
Меньше зависимостей; один раннер для юнитов и e2e. Пересмотреть на этапе 0б, если
понадобятся отчёты и ретраи `@playwright/test`.

**D-020. Роли агентов - план, реализация после этапа 0б.** (владелец)
Общие роли (ревьюер, тестировщик, дизайнер, приёмщик) уже есть в `global-agent-kit/roles`;
новые (планировщик, бизнес-аналитик, безопасность) - туда же, в проект - только факты.

## 2026-09-25 - сессия №2, этап 0б

**D-021. Офлайн-сборка Vite - свой плагин в `@gf/vite-config`, а не `vite-plugin-singlefile`.** (агент)
Нужно ровно одно: классический скрипт (IIFE) внутри HTML в конце `<body>`, CSS и ассеты
встроены. Готовый плагин оставляет `<script type="module">` и тянет `rollup` в peer-зависимости
при Vite 8 на Rolldown. Свой - 60 строк, покрыт юнит-тестами (`inline.test.ts`), сборка
падает, если хоть один чанк не встроился. Вне офлайна тот же формат IIFE - одинаковое
поведение в хабе и в архиве. Цена: без top-level `await` (П-018).

**D-022. UI хаба - Tailwind 4 + компоненты в стиле shadcn/ui, написанные вручную.** (агент, в рамках D-003)
Реестр `ui.shadcn.com` из среды агента закрыт (403), `shadcn init` не запустить. Компоненты
(`Button`, `Card`, `Badge`) повторяют код shadcn: `cva` + `clsx` + `tailwind-merge`, токены
цветов в CSS-переменных. Когда реестр откроется, их можно заменить на сгенерированные
без правки страниц. Radix пока не нужен: интерактивных примитивов нет.

**D-023. Хаб читает `registry.json` с диска, файлы игр не отдаёт.** (агент)
Этап 0: реестр - файл, общий с play-server (`GF_DATA_DIR`, в Docker - том только для чтения).
Обложки и архивы отдаёт служебный хост play-server, хаб лишь ставит ссылки - хаб не
касается содержимого игр. Страницы динамические (`force-dynamic`): после `gf build` каталог
обновляется без пересборки хаба. На этапе 1 чтение уходит в Postgres за тем же `listGames()`.

**D-024. Права манифеста → атрибуты iframe в `hub-bridge` (`frameAttributes`).** (агент)
Одна функция на хаб и тесты: `sandbox` всегда `allow-scripts allow-same-origin`
(+ `allow-pointer-lock` по праву), `allow` - только то, что игра попросила (`fullscreen`,
`gamepad`, `audio`→`autoplay`). Игрок в хабе - гость (`player: null`) до авторизации (этап 1).

**D-025. Шаблоны игр - пакеты рабочей области; новая игра - `gf new <id>`.** (агент)
`templates/vite-ts` собирается и проверяется типами вместе со всеми, поэтому не протухает.
`gf new` копирует его без `node_modules`/`dist` и подставляет id. id игры в код попадает
при сборке (`__GF_GAME_ID__` из `game.json`) - не разъедется с манифестом.

**D-026. Turborepo по-прежнему не нужен (уточняет D-002).** (агент)
Замер 2026-09-25: сборка хаба ~10 с, игр ~2 с, весь `pnpm check` ~50 с. Кеш задач не
окупит ещё одну зависимость. Вернуться, когда `pnpm check` перевалит за 3-5 минут.

**D-027. `docker-compose.yml` - стенд разработчика, не прод.** (агент)
Один `Dockerfile` с целями `hub` (Next `standalone`) и `play` (ядро без `node_modules`).
Игры собираются на хосте и монтируются томом только для чтения. Контейнеры: не root,
ФС только для чтения, `cap_drop: ALL`, `no-new-privileges`, порты только на `127.0.0.1`.
`standalone` включается переменной `GF_HUB_STANDALONE=1` только в образе: `next start`
с ним не работает, а e2e и локальный запуск идут через `next start`.

**D-028. Хаб на этапе 0б - минимальные защитные заголовки, полная CSP - этап 1.** (агент)
Сейчас: `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `nosniff`, COOP,
без `X-Powered-By`. Полная CSP для скриптов Next требует nonce и динамического рендера
всего хаба - делается вместе с авторизацией, когда появится что защищать.

**D-029. Демо-игры не грузят ассеты файлами.** (агент)
Текстуры Phaser рисуются `Graphics.generateTexture`, Three - геометрия кодом. Загрузчики
движков ходят через XHR/fetch, а в архиве `file://` это запрещено (П-002). Для игр
с картинками - импорт файла в код (Vite превратит в `data:`-URL при `offline: true`).

**D-030. На этапе MVP всё коммитится прямо в `main`.** (владелец) - *заменено D-042: работа идёт в `dev`*
Без веток и PR, по одному коммиту на сессию с "да" владельца. Облачная среда заводит
на каждую сессию ветку `claude/<тема>-<случайный хвост>` - это её механизм, а не решение
проекта; в неё не пушим. Пересмотреть при открытии платформы или появлении второго человека.

**D-031. Минуты CI экономим.** (владелец: "не трать лишний раз CI-минуты")
- CI не запускается на коммиты, где правлена только документация (`paths-ignore`).
- Сборка Docker-образов - отдельный workflow, только при изменении `Dockerfile`,
  `docker-compose.yml`, `.dockerignore`, lockfile, или вручную.
- Dependabot - раз в месяц, минорные и патчи одним PR на экосистему; мажоры - отдельно.
- Обновления, которые агент может проверить сам, вливаются в коммит сессии, а не мержатся
  по одному PR (каждый мерж - ещё прогон CI).

**D-032. TypeScript 7 во всём репозитории, Playwright 1.63.** (агент, владелец поручил разобрать PR Dependabot)
TS 7 (нативный компилятор) проверен локально: `pnpm typecheck` чист, `erasableSyntaxOnly`
и ошибки типов ловит; `next build` хаба на TS 7 типы проверяет и падает на ошибке (проверено
мутацией). Playwright 1.63: 20/20 e2e на Chromium 141 из облачной среды (`GF_CHROMIUM_PATH`, П-030).
Actions: checkout 7, setup-node 7, upload-artifact 7, pnpm/action-setup 6. PR Dependabot #1-#4,
#6, #7 этим поглощены.

**D-033. Деплой на VPS - сейчас, за уже настроенным Traefik.** (владелец; заменяет D-017 в части деплоя)
Приёмку этапа 0б негде провести без стенда, а на VPS уже есть Traefik с сертификатами.
Настраивает отдельная сессия агента на самом VPS по `docs/specs/deploy-vps.md`.
Рекомендации спецификации (окончательный выбор - в той сессии, с владельцем): образы в
GHCR из CI после зелёного `CI`; доставка - таймер на VPS тянет образы (в GitHub нет ключей
от сервера); self-hosted runner отвергнут - репозиторий публичный; игры публикует
одноразовый контейнер `games` в постоянный том, чтобы неизменяемость версий действовала в проде.

**D-034. Игры собираются в CI, на сервере - только публикация.** (владелец: "да, лучше в ci собирать игры")
Спецификация предлагала собирать игры одноразовым контейнером прямо на VPS. Памяти на VPS-1
на это мало (разведка 2026-09-25), а Vite с Phaser/Three - самая тяжёлая сборка проекта. Поэтому образ `games` собирается в CI (стадия `games-build` в `Dockerfile`),
а на сервере запускается `gf build --prebuilt && gf export`: `--prebuilt` берёт готовый `output`
вместо запуска `pnpm run build`. Проверка неизменяемости - тот же код `gf build`, что локально.
Отвергнуто: сборка на сервере (память); готовый том в образе без `gf build` (терялась бы
неизменяемость - главная причина держать постоянный том).

**D-035. Прод-конфиг на сервере - копии root, не рабочая копия.** (агент)
`docker compose` и `gf-update` запускает `root`. Если бы они читали `compose.yml` и скрипт из
рабочей копии агента, правка файла под пользователем агента давала бы `root` (compose умеет
смонтировать `/`). Поэтому `deploy/*` ставится `install` в `/etc/docker/containers/game-factory/`
и `/usr/local/sbin/gf-update`. Цена: правка `deploy/` требует переустановки (OPERATIONS.md).

**D-036. Веб - на отдельном адресе VPS-1.** (владелец, 2026-09-25)
Под веб владелец взял отдельный адрес `2.26.198.231`; почему и что с остальными адресами -
в приватной базе инфраструктуры (D-039, D-043). Для проекта это только запись DNS.

**D-037. Репозиторий и образы - публичные; доставка - таймер на сервере.** (владелец: "давай сделаем репу публичной")
Репозиторий был приватным, хотя STATE сессии №2 считал его публичным. Сделан публичным
2026-09-25 после проверки истории на секреты (ключей, токенов, адресов, почты нет).
Пакеты GHCR - тоже публичные: серверу не нужен токен `read:packages`. Доставка - вариант А
спецификации: таймер на VPS-1 тянет образы; self-hosted runner по-прежнему отвергнут
(публичный репозиторий - чужой код из PR на сервере), SSH из GitHub - ключ от сервера в GitHub.
Сертификаты: `*.play` - через DNS-01 (резолвер `dns01` в метках compose), `games` - HTTP-01.

**D-038. Хаб и сервер игр - в своей внутренней сети `gf-edge`; веб-адрес закрыт для всего, кроме 80/443.** (владелец: "давай как-то попробуем закрыть дыры"; 2026-09-26)
Взлом хаба (Next.js - самая крупная поверхность) не должен давать доступа ни к чему, кроме
самого хаба. Сделано:
- сеть `gf-edge` с `--internal` - в ней только наши два контейнера и Traefik (подключается
  к ней на лету, без перезапуска): ни чужих контейнеров, ни выхода наружу;
- правила файрвола хоста: из `gf-edge` - не на хост, на веб-адресе - только 80/443.
  Сами правила - настройка сервера, в приватной базе инфраструктуры (D-043).
Отвергнуто: общая сеть с чужими контейнерами; закрывать их правилами по одному (хрупко).

**D-039. В публичном репозитории - ничего об инфраструктуре сверх необходимого.** (владелец: "чувствительную инфу не оставляй, т.к. репа публичная"; 2026-09-26)
Не пишем: адреса сервера кроме веб-адреса (он и так виден в DNS), что ещё крутится на
сервере, служебные порты и панели, итоги аудитов, id записей DNS, пути к секретам.
Это живёт в приватной базе инфраструктуры, здесь - ссылка. Уточнено D-043.
История git до этого решения содержит часть таких деталей (коммиты 2026-09-25…26);
владелец переписал её 2026-09-26 (`git filter-repo`: детали → `***`, почта автора → noreply),
хеши коммитов до этой даты в документах недействительны.

**D-040. "Звездопад": уровни сложности вместо разброса скоростей.** (владелец, 2026-09-26)
Было: скорость каждой звезды - `120 + счёт × 6 + случайные 0…60`; на высоком счёте соседние
звёзды падали с разной скоростью и некоторые поймать было нельзя. Стало: уровень растёт
каждые 20 секунд, все звёзды уровня падают с одной скоростью (`140 + 25 × (уровень - 1)`),
платформа ускоряется вместе с ними (×2,6 от скорости звёзд). Уровень виден в панели, при
повышении - надпись и новый цвет звёзд. Версия 1.1.0 (неизменяемость, П-034).

**D-041. Обложка: версия в адресе и годовой кеш только для текущей версии.** (агент, сессия №4, 2026-09-26; ROADMAP "Слабые места")
Хаб просит `/covers/<id>?v=<version>`. Сервер игр отдаёт `Cache-Control: public,
max-age=31536000, immutable`, только если `v` совпал с текущей версией из реестра; без `v`
или со старой - `no-cache` и `ETag` (`<хеш версии>-cover`, 304 на `If-None-Match`).
Почему так: версия неизменяема (инвариант 2), значит адрес с версией навсегда значит одни
байты. Долгий кеш на адресе без версии или с чужой версией после смены или снятия игры
держал бы у игрока не ту картинку до года.
Отвергнуто: хеш вместо версии в адресе (то же самое при соблюдённом инварианте 2, но
нечитаемо); версия в пути (`/covers/<id>/<version>`) - та же суть, больше правок маршрута;
404 на старую версию - хаб, не успевший перечитать реестр, остался бы без картинок;
`preconnect` к служебному хосту - `<img>` и так в первом HTML, выигрыш на первом открытии
мал, а долгий кеш снимает запрос на всех следующих.

**D-042. Ветки: `dev` - работа, `main` - прод.** (владелец, 2026-09-26: "раз у нас появился
ci/cd, давай добавим ветку dev, которую, когда нужно, будем сливать с main"; заменяет D-030)
- Все коммиты сессий - в `dev`. Пуш в `dev` гоняет CI (и Docker, если менялись его файлы),
  но в прод не едет: Publish смотрит только на `main`.
- Выкладка на прод = перенос `dev` в `main` - только с "да" владельца и только перемоткой
  (`git push origin origin/dev:main`, без force): история `main` всегда - начало истории `dev`.
  CI на `main` прогоняется ещё раз на том же коммите - это цена ворот перед продом,
  выкладки редкие.
- PR `dev` → `main` не открываем: CI прогнался бы и на PR, и на `main` (D-031).
- Dependabot - в `dev` (`target-branch`).
- **Новые ветки - только с разрешения владельца** (владелец: "никогда не создавай новые
  ветки без моего разрешения"). Ветку `claude/…`, которую просит облачная среда, не создавать
  и не пушить.
- Минуты: для публичного репозитория стандартные раннеры GitHub бесплатны (по документации
  GitHub; на аккаунте владельца не проверено) - D-031 остаётся как вежливость к очереди и времени.
Отвергнуто: git-flow с `release/*` и `hotfix/*` - на одного человека лишние ветки;
защита `main` правилами GitHub - пока не нужна, пушит только владелец и агент с его "да".

**D-043. О сервере в репозитории - только то, без чего не работает проект (уточняет D-039).** (владелец, 2026-09-26: "проверь ВСЕ файлы документов, чтобы там не было информации о сервере"; "в инфру ничего не нужно выносить")
Почему понадобилось: D-039 перечислял категории, но сессия на VPS-1 всё равно записала
в STATE, DECISIONS, OPERATIONS и спецификацию итоги разведки и аудита - как "проверено".
Правило было, проверки перед коммитом не было.
- **Можно:** домены и веб-адрес (видны в DNS); файлы `deploy/` и пути, куда они ставятся
  (без них не установить прод); наши меры защиты - что сделано, без подробностей чужого.
- **Нельзя:** ОС и версии ПО сервера; память, диск, swap; что ещё работает на сервере и на

  и глазами по списку "нельзя": шаблон ловит не всё.

  в ней нет (проверка по шаблонам токенов и ключей, 2026-09-26); детали сервера из коммитов

## 2026-09-26 - сессия №5 (облако): приёмка 0б, слабые места, план

**D-044. `gf check-prod` в CI: хеш собранной игры сверяется с продом.** (агент; владелец: "делай слабые места")
Прод отдаёт метку содержимого (`contentTag` - 16 символов хеша версии) в начале ETag файла
игры и `id@version` в `X-GF-Game`. Этого хватает, чтобы до выкладки понять: та же version,
другое содержимое → прод не опубликует (П-034). Шаг CI после `games:build` (на `dev` и `main`):
такой случай - красный CI с подсказкой "подними version". Прод не ответил или игры на нём
нет - предупреждение, не красный: сверка - подсказка, а не ворота выкладки.
Сборка воспроизводима между облаком и CI/Docker - проверено: хеши локальной сборки всех
трёх игр совпали с ETag прода (сессия №5).
Отвергнуто: lock-файл хешей в репозитории - сверял бы репозиторий сам с собой, требовал бы
правки на каждое изменение игры, а `--replace` переписал бы его под уже опубликованную версию.
Попутно: 304 по `If-None-Match` перенесён в `streamFile` - теперь и у архивов, а не только у
файлов игр и обложки.
