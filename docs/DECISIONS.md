# Журнал решений

Формат: **что решили** → почему → что отвергли. Отменённое не удаляется, а помечается
«заменено D-0xx». Источник: `владелец` — решил человек; `агент` — предложил агент,
владелец принял или не возражал.

## 2026-09-25 — сессия планирования и скелет MVP

**D-001. Основной язык — TypeScript; другие языки — через WASM и контейнеры.** (владелец)
Один язык для хаба, игр, SDK и ИИ-агента; у ИИ по TS больше всего обучающих примеров.
Другие языки: клиент игры — Rust/C/C++/Go/C# через WASM или готовый экспорт движка
(поле `toolchain`); бэкенд игры — любой язык в контейнере (этап 3).

**D-002. Монорепо: pnpm workspaces; Turborepo — когда появятся тяжёлые сборки.** (агент)
Пока задач немного и они быстрые — хватает скриптов pnpm. Turborepo добавим вместе с
Next.js и Vite (этап 0б), когда кеш сборок начнёт окупаться.

**D-003. Хаб и админка — Next.js + shadcn/ui.** (владелец)

**D-004. Сборка игр — Vite.** (владелец)

**D-005. Движки: Phaser 4 (2D), PixiJS v8 (2D-рендер), Three.js (3D), Rapier (физика), Howler.js (звук).** (агент, владелец доверил выбор)
Phaser — движок целиком, быстрый старт. Pixi — когда нужна своя архитектура. Three —
стандарт 3D в вебе. Rapier — WASM, детерминированная, 2D и 3D. Отвергнуто: Babylon.js
как дефолт (тяжелее, для «движка целиком» в 3D — позже, если понадобится).

**D-006. Очередь задач — BullMQ на Valkey, за своим интерфейсом `JobQueue`.** (агент, владелец спросил про RabbitMQ)
Задачи (сборка, превью, ИИ-агент) — это «задание с повторами, таймаутом и прогрессом»,
ровно то, что делает BullMQ. Valkey всё равно нужен для лидербордов, лишнего сервиса нет.
RabbitMQ отвергнут: брокер для обмена событиями между многими сервисами на разных
языках — у нас воркеры на TS, а бэкенды игр в очередь не ходят. Если понадобится
шина событий между языками — NATS (легче RabbitMQ).

**D-007. Файлы — S3: MinIO локально, свой S3 по профилю хранилища.** (владелец)
Профили хранилищ в админке: endpoint, регион, бакет, ключи; игре можно назначить профиль.
Ключи в БД — зашифрованы мастер-ключом из файла с правами `600`, ввод — скрытым полем,
после сохранения видно только «задан, длина N».

**D-008. Игра = пакет с манифестом `game.json`.** (агент)
Хаб не зависит от того, чем игра собрана. Манифест строгий: неизвестные поля — ошибка.

**D-009. Домены: хаб `games.youranus.ru`, игры `<id>.play.youranus.ru`.** (владелец + агент)
Владелец хотел `*-play.youranus.ru` — так нельзя: wildcard в DNS и сертификатах бывает
только на целую левую метку (`*.что-то`). Поэтому `*.play.youranus.ru`. Сертификат —
бесплатный wildcard Let's Encrypt через DNS-01; нужен API DNS-провайдера для автопродления.

**D-010. До открытия платформы игры живут на поддомене того же домена; перед открытием — отдельный домен.** (владелец)
Цена компромисса: хаб и игры — «один сайт» для браузера (same-site), SameSite-cookies не
защищают хаб от CSRF со стороны игр; игры могут ставить cookies на `youranus.ru`.
Меры сейчас: кука хаба с префиксом `__Host-`, CSRF-токены и проверка `Origin`. Перед этапом 5
владелец покупает отдельный домен для игр и вносит его в Public Suffix List.

**D-011. Пока всё на одном VPS; разделение «доверенная / грязная» машина — перед открытием.** (владелец)

**D-012. Офлайн-архив — сейчас только для статических игр.** (владелец)
Простые игры на HTML/CSS/JS скачиваются сразу. Игры с бэкендом, S3 и т. п. — отдельный
разговор (этап 3: `docker-compose.yml` + статика).

**D-013. Ядро — без npm-зависимостей.** (агент)
play-server, CLI, манифест, реестр, SDK, мост — только стандартная библиотека Node.
Почему: play-server стоит на «грязной» стороне, каждая зависимость — поверхность атаки и
цепочка поставок; ядро мелкое и хорошо тестируется. Вынужденная причина в этой сессии —
реестр npm был закрыт, но решение осталось бы и без неё. Отвергнуто: zod в ядре (zod будет
в хабе для API), fflate/yazl для записи zip (запись — 100 строк; **чтение** чужих архивов
на этапе 2 пойдёт через проверенную библиотеку — там самописный парсер опасен).

**D-014. SDK — классический скрипт с JSDoc-типами, а не ES-модуль.** (агент)
Модульные скрипты не грузятся через `file://`, а офлайн-архив открывается именно так.
Один исходник работает везде: `<script src="gf-sdk.js">` в статике, `import '@gf/game-sdk'`
в Vite (обёртка `index.js`). Типы — `index.d.ts`, проверка — `tsc --checkJs`.

**D-015. Опубликованная версия неизменяема.** (агент, владелец принял правила песочницы)
Та же `version` с другим содержимым — отказ сборки. Откат — переключение указателя
на прошлую версию. `--replace` — только для локальной отладки.

**D-016. TypeScript исполняется Node напрямую (type stripping), без сборки.** (агент)
Node ≥ 22.18. Ограничения — только стираемый синтаксис, импорты с `.ts`. Отвергнуто:
tsx/ts-node (лишние зависимости), сборка ядра в JS (лишний шаг и рассинхрон).

**D-017. CI/CD — GitHub Actions; деплоя на VPS пока нет.** (владелец)
Владелец запускает сессии агентов на том же VPS; деплой — отдельное решение позже.
CI: типы, юнит, сборка игр, офлайн-архивы (артефакт workflow), e2e в Chromium.

**D-018. Service Worker на поддоменах игр запрещён (этап 0).** (агент)
SW переживает смену и даже снятие версии игры и продолжает отдавать старое содержимое
со своего origin. play-server отвечает 403 на запрос скрипта SW (`Service-Worker: script`).
Пересмотреть, если появится игра, которой нужен офлайн-кеш в браузере.

**D-019. Тесты — `node:test` + Playwright как библиотека, без тест-раннеров.** (агент)
Меньше зависимостей; один раннер для юнитов и e2e. Пересмотреть на этапе 0б, если
понадобятся отчёты и ретраи `@playwright/test`.

**D-020. Роли агентов — план, реализация после этапа 0б.** (владелец)
Общие роли (ревьюер, тестировщик, дизайнер, приёмщик) уже есть в `global-agent-kit/roles`;
новые (планировщик, бизнес-аналитик, безопасность) — туда же, в проект — только факты.
