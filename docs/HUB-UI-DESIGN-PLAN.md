Точные значения, переданные владельцем (`#`-комментарии из сообщения не являются CSS):

```css
@media (any-pointer: coarse) {
  [data-catalog-prototype="c"] .gf-catalog .gf-card__actions {
    --action-height: calc(2rem + .1875rem);
  }
}
[data-catalog-prototype="c"] .gf-catalog .gf-card__body {
  gap: .375rem;
  padding: .5rem .75rem .5rem;
}
[data-catalog-prototype="c"] .gf-game-tags__more {
  width: 2rem;
  height: 1.375rem;
}
```

Coarse-override кнопки «…» с размерами 48 px удалить, иначе он сильнее базового
правила. При rem=16 текущая формула даёт 32 px основной кнопке и 35 px скачиванию,
с учётом отдельной нижней тени; «…» — 32×22 px. Эти размеры не выдаём за 48 px.
При увеличенном тексте сохраняется возможность естественного роста/перестройки.

| 2 | Ориентир ПК: обычная шапка с навигацией/аккаунтом, три колонки, два полных ряда | Скрин страницы продакшена со слов владельца; точный CSS viewport/zoom не измерен |

| 4 | Проблемная граница первого экрана landscape, видны фрагменты ряда тегов | DevTools 844×390; по одному снимку нельзя доказать выход тегов именно за карточку |

Сохраняем исходники/базы; утверждённые эталоны создаём отдельно после выбора дизайна.
Конкретные CSS-правки владельца получены и зафиксированы выше. PNG сам по себе
не содержит значений CSS и размеров невидимых hit areas. Экспорт/сверка выполняется при одинаковых шрифтах,
данных, масштабе, теме, CSS viewport и состоянии ввода.
Fit to window уменьшает вид всего эмулятора: физические пиксели такого PNG
не являются размерами элементов в CSS px.

Контракт разделяет две вещи: **устойчивую композицию** и **видимое количество
контента на определённом viewport**. На всей полосе ширин 314–440 px можно сохранить
одинаковые типографику, отступы, компоненты и поведение. Одинаковые две полные
карточки на всех ширинах и высотах не гарантируются: полноширинная обложка 16:9
становится выше при увеличении ширины. Нельзя компенсировать это обрезкой обложки,
мелким текстом или возвратом зависимости высоты карточек от панели браузера.

Плотность мобильного примера проверяется с компактными размерами, выбранными
владельцем выше. Общий прежний порог 48 не применяется к этим действиям карточки
и кнопке «…»; остальные интерактивные элементы проверяются по своему контракту.
Тень не является hit area; зоны не перекрывают описание и соседние действия.

Предлагаем файл **Game Factory — Hub UI**, со страницами:

- `References`: снимки владельца, исходный сайт и непринятые варианты с подписями.
- `Foundations`: обе темы, текущие шрифты/цвета, интервалы, радиусы, размеры,

- `Components`: кнопки, карточка, версии, теги/«…», desktop/mobile header,

- `Layouts`: 314/320/360/390/425/440 px, переход после 440 px, планшеты, landscape,
  Full HD/QHD/4K и окна 1920×920 / 2560×1280. Сначала каталог, затем остальные страницы.
- `Motion`: открытие/закрытие меню, диалога и уведомления, backdrop, reduced motion.
- `Approved`: только принятые версии с датой, ссылками node/frame и контрактами адаптива.

Одного помещения PNG в Figma недостаточно. Нужны редактируемые компоненты,
переменные, Auto Layout, ограничения ширины и указания поведения между фреймами.
Сначала восстанавливаем эталоны, затем проверяем stretch на промежуточных ширинах.
Для компонента фиксируем связь Figma-node ↔ React/CSS-компонент, общий набор токенов
и способ их переноса. Не создаём две независимо редактируемые копии токенов.

Фактическое ограничение подключённого Starter: три страницы и один mode переменных
на коллекцию. Поэтому foundations размещены в коллекциях/стилях, а motion и будущая
секция Approved — на `Layouts`; отдельные страницы для них не создаём. «Ночь» и
«День» представлены отдельными коллекциями с одинаковыми CSS-именами токенов.

Новый порядок: **дизайн и состояния в Figma → принятие конкретных фреймов/правил →
реализация существующими компонентами → браузерные снимки и наложение на эталон**.
Figma не воспроизводит панель Chrome, hit testing, клавиатуру или iframe;
браузерная приёмка сохраняется. Для изменения прежнего источника дизайна учитываем
существующее решение D-057; новую договорённость фиксируем в рабочем плане,
глобальные журналы этой локальной сессией не переписываем.

## 3. Контракт адаптива до кода

Предложение, численные пороги ещё предстоит проверить во фреймах:

- **Узкий телефон до 440 px включительно:** одна колонка, бренд+бургер,
  две строки описания, естественный заголовок и компактные видимые действия
  по №1 с доступными touch-целями. Состав первого экрана задаём по каждому эталону,
  а не обещаем одинаковое число карточек на любом телефоне.
- **После 440 px:** отдельная проверка диапазона 441–767, затем две колонки,
  когда помещаются обложка, текст и оба действия. Не переключаем раскладку
  на ширине 441 только потому, что закончился диапазон маленького телефона.
- **Планшет:** две колонки; портрет/landscape проверяются отдельно.
- **ПК:** композиция №2 — размер контейнера и карточек, обычная шапка,
  интервалы и читаемый масштаб. Бургер не заменяет desktop-навигацию.
  Цель — два полных ряда на перечисленных опорных окнах; она проверяется
  вместе с масштабом и распределением пространства, а не только числом рядов.
- **Landscape телефона:** свой осмысленный макет в Figma. Проверяем теги внутри
  карточки, целые чипы и кнопку «…», отсутствие внутреннего clipping/пересечений,
  видимые фрагменты у нижнего края первого экрана и доступность карточки после скролла.
  Не исправляем дефект простым `overflow:hidden` и не выдаём обрезку viewport
  за доказанный выход за границу карточки.

В текущем C высоты действий зависят от `any-pointer:coarse`, а в исходном хабе —
также от `pointer:coarse`. Поэтому DevTools с узкой шириной и вводом мышью
может отличаться от телефона. Новый контракт должен сохранять визуальный профиль
по ширине/тексту; наличие касаний определяет доступность и hit area,
а не неожиданно заменяет всю композицию на том же размере.

Карточки — CSS-компоновка по ширине и контенту. Обложки contain/16:9,
пустые поля не резервируют строки, footer выравнивается в ряду.
Никакой обратной связи «измерили карточку → рассчитали её же высоту».
Высота visualViewport, dvh и прокрутка не управляют геометрией каталога,
включая косвенные изменения rem и media queries. Реальный поворот/resize
и пользовательское увеличение текста должны обрабатываться отдельно.

## 4. Один общий компонент всплывающих поверхностей

Композиция компонентов, а не копирование разметки или наследование React-классов:
общий `Popup`/`Overlay` с вариантами `dialog` и `drawer`; общее управление
присутствием/анимацией используется также у уведомлений и немодальных popover.
Семантика разная: toast не получает modal, затемнение и ловушку фокуса.

Общий контракт по умолчанию:

- Состояния `closed → opening → open → closing → closed`.
- Анимации **обеих** сторон и backdrop заданы по умолчанию. Закрытие крестиком,
  Escape, нажатием снаружи и программно проходит один путь; `.close()`/unmount
  выполняется после выхода, а не мгновенно обрывает анимацию.
- Общие токены времени/easing; корректный быстрый повтор открытия/закрытия,
  очистка при навигации, отмена анимации и отсутствие зависания закрывающегося слоя.
- Для модального варианта: подпись, начальный фокус, Tab/Shift+Tab, Escape,
  возврат фокуса, неактивный фон, контролируемая прокрутка без сдвига страницы.
- `prefers-reduced-motion`: уважать системное ограничение движения;
  закрытие и очистка не зависят от обязательного проигрывания анимации.
- Контент/действия передаются в общий компонент; анимации не требуется
  отдельно вспоминать и прописывать в каждом новом потребителе.

Первыми потребителями становятся меню и диалог тегов; далее инвентаризируем
реальные уведомления/прочие поверхности и добавляем их примеры в `/kit`.
В текущем коде GameTags анимирует только появление и напрямую вызывает close,
а прототипное меню не имеет входа/выхода: это нужно исправлять на общем уровне.
Правило для `apps/hub/AGENTS.md` и узкая CI-проверка: новые popup-потребители
используют общую основу; самостоятельный `<dialog>` остаётся внутри её реализации.
Статические иллюстрации в kit отделяются от реальных интерактивных примеров явно.

### Выдвижное меню

- Только в профилях с бургером; на ПК сохраняется шапка №2.
- При открытии панель входит справа; при закрытии уходит вправо с fade-out,
  backdrop плавно появляется и исчезает. Ширина — `calc(100% - 70px)` viewport,
  справа без отступа; **border: 0**. Высоту, safe areas и скролл проверяем отдельно.
- Активная ссылка получает `.is-active` и `aria-current="page"`.
  Фон задаётся самому элементу; `::after` для этого не используется.
  Элемент имеет внутренние отступы и скругление. Отступы между пунктами сохраняются.
  Desktop-стили активной ссылки не переопределяются глобально.

## 5. Перенос и сравнение

Сначала принятые токены/компоненты, затем popup и drawer, карточка и каталог,
потом остальные страницы из исходного плана. Один общий набор компонентов
используется в Next и превью. Шапка больше не остаётся отдельной копией прототипа.

Для каждого принятого фрейма сохраняем его node URL, экспорт/снимок, размеры,
шрифты, данные и вариант ввода. После реализации сравниваем соответствующий
снимок браузера с Figma: по умолчанию ручной просмотр владельцем масштаба,
пропорций, пустот и фактического контента первого экрана. Эталон не обновляется
автоматически ради зелёного CI. Любое отступление описывается и показывается.
Наложение/diff и повторный запрос дизайна через интеграцию — адресно при
заметном расхождении или отдельном запросе, а не на каждой итерации.

Особенно проверяем 439/440/441 и соседние размеры настоящих брейкпоинтов,
mouse/touch/hybrid, обе темы, длинные/пустые поля, текст 200%, неполную высоту окон.
Новый тест должен падать при возвращении соответствующего старого дефекта.

## 6. Что считается проверенным

- Карточки: геометрия в документе стабильна при scroll/visual viewport (≤1 CSS px),
  изображения разных исходных пропорций показаны целиком, нет пересечений текста,
  теги внутри карточки, действия имеют неперекрывающиеся hit areas.
- Попапы: фиксируются промежуточные кадры **открытия и закрытия** панели/backdrop,
  все способы закрытия, быстрые повторы, reduced motion и клавиатура.
  Проверка наличия CSS animation в исходнике не заменяет воспроизведение.
- Визуальная приёмка: и размеры/раскладка, и читаемый масштаб/композиция относительно
  принятого фрейма; «два ряда поместились» само по себе не является успехом.
- Настоящий Next и реальная игра в iframe, прежние страницы/состояния и
  существующая UI-матрица; затем короткие регрессии в CI и независимое ревью.
- Физический Chrome Android через прямой URL/ADB, скрытие панели, клавиатура,
  поворот; Safari iPhone — отдельная проверка или явный непроверенный пункт.

Этот план не запускает авторизацию, роли и экономику. Разрешение на commit/push/
merge/ветки/публикацию не меняется. Владелец после просмотра Figma и уточнений R2
разрешил перенос в приложение. Фактический ход реализации и проверки —
[HUB-UI-IMPLEMENTATION-REPORT.md](HUB-UI-IMPLEMENTATION-REPORT.md).
