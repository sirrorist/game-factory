# Почтовый транспорт: подготовка владельцем

Локальный первый подшаг 2А-03 реализует транспорт, но не подключает его к auth.
Resend Free выбран по D-063. По скриншоту владельца auth.youranus.ru Verified,
Ireland; со слов владельца создан ограниченный Sending access ключ. Сам ключ,
tracking, фактическая сеть и реальная отправка не проверены. Команды ниже — инструкция для будущего отдельно согласованного подключения,
а не разрешение запускать сервисы сейчас.

## Аккаунт и домен

1. Создать аккаунт Resend Free.
2. Согласовать отправителя. Предложение: Game Factory, адрес
   noreply@auth.youranus.ru. Добавить поддомен в Domains и внести именно показанные
   Resend DNS-записи для отправки; подтвердить домен.
3. Отключить open/click tracking для служебных писем.
4. Создать ключ с разрешением только на отправку и ограничением выбранным доменом.
   Значение не передавать в чат, репозиторий, аргументы команд или журналы.
5. Проверить квоту команды и другие использующие её приложения. Документированные
   Free-квоты на дату плана — 100 писем в день UTC и 3000 в месяц, включая входящие.
   API rate limit команды проверяется отдельно. Исчерпанная квота не запускает
   автоматическую платную подписку или немедленную серию повторов в нашем коде.

Настоящий ящик для этого исходящего транспорта не создаётся. Собственная почта
с приёмом и хранением остаётся будущей отдельной задачей ROADMAP.

## Конфигурация и профиль v1

Шлюз запускается только с полным набором:

| Переменная | Значение |
|---|---|
| GF_HUB_ORIGIN | Точный HTTPS origin хаба без завершающего слеша |
| GF_MAIL_FROM | Один согласованный адрес отправителя, без display name |
| GF_MAIL_PROFILE_SHA256 | Сохранённый SHA-256 профилей v1: origin, отправитель, темы и оба шаблона |
| GF_MAIL_SERVICE_SECRET_FILE | Файл случайного служебного секрета, общий только хабу/шлюзу |
| GF_RESEND_API_KEY_FILE | Файл ключа Resend, доступен только шлюзу |

Служебный секрет — 32 случайных байта в hex (64 символа); код допускает 32–256
символов A–Z/a–z/0–9/_/-. Ключ Resend должен иметь формат re_ с непустой основной
частью. Отсутствующие/пустые/неверные значения закрывают запуск. Файлы создаёт
владелец скрытым вводом; агент реальные файлы не читает. Права файловых секретов
согласовать по П-044, не рассчитывать на uid/mode compose как доказательство доступа.

Вычисление начального pin — пример для локальной копии проекта, оболочка Bash;
адреса ниже демонстрационные, их нужно заменить согласованными. Секретов в команде нет:

~~~bash
node --input-type=module -e 'import { createProfiles, profileFingerprint } from "./apps/mail-relay/src/config.ts"; console.log(profileFingerprint(createProfiles("https://hub.example.com", "noreply@auth.example.com")))'
~~~

Pin сохранить вместе с исходным профилем. Не пересчитывать его автоматически при
запуске и не менять для принятия новых текстов/отправителя под прежним v1.
Изменение профиля требует новой версии kind с сохранением старой минимум на
24 часа возможных повторов. Сейчас реализованы только два v1-профиля; добавление
следующей версии — отдельное изменение. При расхождении pin шлюз не запускается.
В тестах сохранён контрольный pin профиля с демонстрационным адресом.

Для хаба нужны GF_HUB_ORIGIN, GF_MAIL_SERVICE_SECRET_FILE и ровно
GF_MAIL_RELAY_URL=http://mail-relay:4102/v1/send. Переменные не включают клиент
автоматически: будущий auth-слой должен явно вызвать hubMailClientFromEnv.

## Подготовленное письмо и повтор

Клиент prepare создаёт body и createdAt, включая единственный случайный operationId.
Снимок можно сериализовать и восстановить restorePreparedMail без замены ID.
Будущий вызывающий хранит его вместе с неизменяемым профилем и состоянием результата;
постоянное хранение ещё не подключено. Не вызывать prepare заново для повтора того же
письма. Клиент send делает один HTTP-вызов, шлюз — до двух upstream-попыток.

Клиент передаёт исходный createdAt + 24 часа обязательным служебным заголовком
X-GF-Mail-Expires-At, не меняющим четыре поля письма и payload Resend. Таймаут
клиента ограничен остатком; шлюз требует, чтобы каждая полная попытка и пауза
помещались до конца окна с резервом 1 секунда. Иначе operation_expired без отправки.
Исходный createdAt нельзя менять при повторе. Перед размещением проверить часы
хаба/шлюза в пределах резерва; синхронизация сейчас не проверена. Монотонный
предел на шлюзе защищает текущий вызов от продления переводом часов назад.
Unknown
после потерянного ответа нельзя трактовать как «письма точно не было».
Not_accepted описывает конкретный вызов и не отменяет неизвестность предыдущего.
Accepted означает только подтверждение приёма провайдером. Незавершённый ответ
после заголовков сохраняет статус/Retry-After, но автоматического повтора нет;
unknown не даёт оснований создавать новый ID для обхода этого результата.

Ссылки сейчас ограничены будущими путями account/verify-email и
account/reset-password с единственным token; сами страницы, токены и переход
на login не реализованы этим подшагом.

## Образы и сеть — отдельный эксплуатационный шаг

Подготовлены [конкретный overlay и команды сохранения секретов](HUB-MAIL-DEPLOYMENT.md).
Владелец разрешил их подготовку, применение ещё не выполнялось. Старый пример ниже
сохранён как иллюстрация и не используется в качестве overlay к продовой конфигурации.

Пример [compose.mail.example.yml](../deploy/compose.mail.example.yml) показывает только
почтовую связь, а не заменяет рабочую конфигурацию. Его нельзя применять как override
к продовому compose без отдельной проверки объединённой конфигурации. Указанные
образы по digest и внешнюю egress-сеть предварительно готовит оператор.

Для шлюза есть отдельный [Dockerfile](../apps/mail-relay/Dockerfile). Он копирует только
исходники и использует стандартную библиотеку Node. База закреплена литералом
Node 22/digest; свободного NODE_IMAGE больше нет. Подготовлены отдельные задачи
CI и Publish, но они ещё не запускались; [результаты и границы](HUB-MAIL-IMAGE-REPORT.md).
Пример ограничивает шлюз 128 МиБ RAM и 0,25 CPU;
это начальные лимиты размещения, не результат измерения контейнера.

Перед реальным запуском оператор отдельно подтверждает:

- отдельную internal-сеть только хаб–шлюз, отсутствие ports и маршрута Traefik шлюза;
- отсутствие у шлюза сетей БД/игр, секретов auth/БД и игровых томов;
- разрешение исходящего соединения шлюза только к Resend HTTPS API и необходимому
  управляемому DNS, сохранение штатной проверки TLS; никаких произвольных прокси;
- успешную проверку нужного API и отказ доступа шлюза к хосту, БД, соседним сервисам
  и постороннему внешнему адресу; сохранение запрета выхода в интернет у хаба.

Compose сам по себе не задаёт доказанного ограничения egress. Правила маршрутизации
и их фактическая проверка выполняются оператором по отдельному плану. В этой
локальной работе они не менялись. Место и правила размещения остаются неутверждёнными.

## Реальная проверка после отдельного разрешения

Отправить одно согласованное тестовое письмо. Разделить результат API, доставку
серверу получателя и фактическое появление во входящих. Зафиксировать только безопасный
результат и дату, без адреса, токена или ключа. Ошибка квоты/конфигурации требует
решения владельца; автоподключения платного тарифа нет.

Открытие регистрационных/recovery-форм потребует следующих шагов Q2/Q3, CSP и
условий общего плана 2А. Этот транспорт не отменяет ни один из них.
