- `readSessionAccess` проверяет статус/поколение/срок, но не доказательство MFA.
  `currentWithPermission` сейчас опирается на такой результат.
- `auth-access.ts` защищает запись credentials и выпуск сессий снимком до

- `auth_recovery_guards` — операторский маркер A, не реализованный фактор.

- В установленном passkey 1.7.7 проверка assertion использует
  `requireUserVerification: false`. Серверный `authentication.afterVerification`
  получает результат verifier до `createSession`: это точка интеграции проверки
  UV, а не готовая гарантия усиленного входа.
- Штатный two-factor 1.7.7 после парольного handler удаляет уже созданную
  сессию; также имеет trust-device и собственные записи/отзывы. Целиком этот
  жизненный цикл не принимается за реализацию нашей двухфазной границы.
- Аварийный `setPassword` отзывает сессии/passkey, но ещё не TOTP/backup codes
  и не выдаёт ограниченный контекст повторной настройки.

## 2. Политика доступа и состояния

Обязательность усиленного входа вычисляется по актуальным данным БД:
`role in (admin, owner) OR enhancedRequired`. Клиент её не назначает.
Наличие TOTP у player/developer в B означает включённую усиленную защиту;
обычный необязательный passkey без такого режима сам по себе её не включает.

| Состояние | Что разрешено |
|---|---|
| Проверен только пароль, усиление обязательно | Только короткое продолжение проверки второго фактора; обычной session-cookie нет |
| Усиленный вход завершён | Обычные действия по действующим permissions и условиям ресурса |
| Есть недавнее повторное подтверждение | Чувствительное действие после повторной транзакционной проверки прав/доказательства |
| Восстановление или первая операторская настройка | Только настройка нового фактора для одной учётки; не роли, игры, данные или обычная сессия |
| Обязательный фактор отсутствует | Закрытый вход; самостоятельная настройка по одному паролю запрещена |

Для admin/owner достаточно UV-passkey **либо** пароля + подтверждённого TOTP.
Резервный код не выдаёт обычную сессию или step-up. Email не подтверждает MFA.
Старые сессии без серверного усиленного доказательства не получают его по роли,
флагу профиля, наличию passkey или повторному чтению поколения.

Проверки действуют одинаково в SSR, HTTP, server API, `currentUser`, проверках
permissions и границе записи adapter. Подтверждение не даёт новых permissions.
Один `actor.userId` не является достаточным основанием будущего веб-действия:
понадобится действующая сессия, поколение и требуемая свежесть доказательства.
Доверенные операторские процедуры остаются отдельным основанием.

## 3. Выпуск и повторное подтверждение сессии

**Пароль + TOTP.** Для учётки с обязательным усилением правильный пароль создаёт
только одноразовый pre-auth-контекст. Он привязан к userId, исходному поколению,
снимку credential, назначению login/reauth и браузеру. Bearer **каждого** pre-auth
и reauth генерируется CSPRNG из 32 случайных байт (256 бит, канонический
base64url); это не последовательный ID и не производная userId/времени.
Каждый выпуск независим от session-token, enrolment, предыдущего контекста
и CSRF. В БД хранится только SHA-256 bearer, срок, состояние и число попыток.
Сам bearer — только в отдельной Secure/HttpOnly/__Host-cookie, SameSite=Strict,
Path=/, без Domain; не в ответе формы, URL, логе или записи БД.
Он не принимается как session-token, CSRF или разрешение credential-write.
Привязка к браузеру означает владение секретом этой cookie вместе с Origin/CSRF,
а не доверие IP/UA или заявленному клиентом browser-ID; она не защищает при
краже самой cookie. Угаданный ID, cookie другого контекста/назначения либо
код TOTP без действительного соответствующего bearer не завершают вход.

Сравнение кода использует фиксированную длину и timing-safe сравнение.
Успех TOTP атомарно потребляет pre-auth, обновляет принятый TOTP-step и создаёт
сессию с серверным усиленным доказательством. Сбой любой записи откатывает всё.
Штатный `/sign-in/email` и прямой server API не могут выдать полноценную
admin/owner-сессию после одного пароля, даже временно до after-hook.
Парольная проверка использует совместимый с Better Auth проверенный scrypt;
новый формат хранения паролей не вводится.

**UV-passkey.** Сохраняются проверка подписи, challenge, точные origin/rpID,
credential/user binding и правила counter verifier. В доверенном hook проверяется
`verification.authenticationInfo.userVerified === true`. Сырые флаги запроса,
настройка клиента `userVerification: required` или наличие ключа этого не заменяют.
Результат связывается с исходным доказательством F1 в request-local контексте;
session и её усиленное доказательство записываются одной транзакцией.
Не поддерживающий UV ключ остаётся обычным ключом, но не открывает усиленный вход.

**Step-up.** Предлагается повторная полная аутентификация допустимым способом.
Для парольного пути проверяются и текущий пароль, и новый TOTP; для passkey —
новый assertion с UV. Challenge имеет назначение reauth, привязан к текущим
userId/sessionId/поколению и исходному bearer текущей сессии; другой пользователь
или recovery-контекст не подходит.
Успех создаёт новую подтверждённую сессию и отзывает прежнюю текущую в той же
транзакции. Старое доказательство не переносится по cookie; другие сессии не
получают step-up. Обычный завершённый усиленный login также считается свежим.

Для user/developer без обязательного/включённого MFA обычная смена пароля требует
свежей повторной проверки текущего пароля. Такое password-only доказательство
не считается усиленным и не подходит после повышения роли/включения MFA.

В БД предлагается связанная с session запись: поколение, метод, время усиленного
подтверждения и credential/factor ID. Proof также неизменяемо связывает
`session.id`, `userId`, поколение, SHA-256 **исходного bearer сессии** и случайный
идентификатор её выпуска. Одной ссылки на session.id недостаточно.
Проверка сравнивает эту связь и с текущей строкой, и с bearer, извлечённым после
успешной проверки подписи **исходной cookie запроса**. Нельзя заменить его
`session.id` или полем `session.token` из произвольного результата getSession.
Server API использует то же основание; переданный вызывающим id не является сессией.

Обновлять proof через профиль запрещено. Он проверяется вместе со сроком session
и активностью учётки; скользящий refresh не меняет bearer/идентификатор выпуска
и не продлевает время усиленного подтверждения. Часы проверки срока — серверные.
Новая чувствительная запись повторяет проверку внутри своей транзакции, а не
доверяет предварительному разрешению страницы. Переназначение роли/фактора или
отзыв между криптографией и записью требуют нового подтверждения.

## 4. Факторы, первичная настройка и секреты

Собственный платформенный контроллер хранит состояния и выполняет транзакции;
two-factor plugin целиком не включается. Для TOTP предлагается небольшая реализация
RFC 6238 на Node HMAC с официальными тестовыми векторами; формат приложения
аутентификатора и окно ниже подлежат утверждению. WebAuthn-криптография остаётся
у установленного verifier, не переписывается. Если его hook/adapter не обеспечат
атомарную запись proof/session, остановить этот участок и предложить узкое
исправление интеграции; не переносить доказательство в клиентский JWT.

TOTP сначала pending: случайный секрет показывается только авторизованной
настройке, зашифрован в БД; до первого правильного кода не считается фактором.
Секрет/otpauth URI не помещаются в URL навигации, внешние QR-сервисы и журналы.
В первом срезе достаточно ручного ввода секрета; QR возможен только локально.
После подтверждения pending не позволяет повторно раскрыть активный секрет.

Каждый проверенный TOTP возвращает конкретный time-step. В транзакции нужно
`acceptedStep > lastAcceptedStep` этого фактора: один код не может повторно
подтвердить login/reauth/настройку в принятом окне, включая два процесса и restart.
Срок challenge и допустимость step перепроверяются при записи. Рассинхронизация
часов не расширяет окно автоматически; синхронизация — условие будущего D.

Для TOTP/pending нужен отдельный файловый 32-байтный key-ring, AES-256-GCM с AAD
по назначению/userId/factorId/версии. Не переиспользовать ключ очереди A, auth-cookie
или Resend. При отсутствии нужного key-id нет plaintext-fallback и отключения MFA.
Ротация должна сохранять чтение действующих факторов либо заранее перешифровать их;
подготовка настоящих ключей и резервное восстановление согласуются в D.

Первый фактор owner/admin и замена полностью утраченного фактора требуют
операторского или резервного enrolment-контекста. Старый пароль/сессия без
усиленного доказательства его не создают. Смена роли на admin/owner отзывает
сессии; отсутствие фактора приводит к ограниченной настройке через оператора.
Роль не выдаётся автоматически при завершении настройки.

Первичная UV-настройка подтверждается assertion нового ключа с UV внутри
ограниченного enrolment; одной регистрации ключа недостаточно. Ранее добавленный
обычный passkey не обходит эту первичную границу по одному паролю. Применить её
нужно также к `create-owner`/`bootstrap-owner` и повышению роли через `set-access`.

При добавлении/замене/удалении факторов в одной транзакции обновляются фактор,
`auth_recovery_guards`, поколение и отзыв сессий/переходных контекстов/старых ссылок.
Для player/developer выключение optional MFA требует действующего step-up;
для admin/owner обязательность не выключается. Последний допустимый фактор нельзя
удалить обычным действием: сначала подтвердить замену либо войти в recovery.
После первичной настройки и восстановления всегда нужен новый усиленный login.
Необязательная регистрация обычного passkey также сохраняет F2 и проверку владельца.

## 5. Смена пароля и восстановление по Q2

| Действие | Основание | Атомарные последствия |
|---|---|---|
| Обычная смена пароля | Текущий credential, сессия и недавнее подтверждение; настроенное MFA обязательно | Новый hash, поколение, отзыв всех сессий/контекстов и старых ссылок; passkey/TOTP и набор recovery codes сохраняются; нового входа нет |
| Почтовый reset | Одноразовое действие A с актуальным email/поколением | Новый hash, отзыв всех сессий/passkey/старых ссылок и переходных контекстов; TOTP и обязательность усиления сохраняются; нет автоматического login/enrolment |
| Восстановление фактора | Одноразовый backup code либо оператор | Отзыв passkey/TOTP/всех backup codes, сессий и чувствительных ссылок; новое поколение и только ограниченный enrolment |
| Аварийный CLI owner | Доверенное операторское подключение | Полный отзыв, новый пароль либо блокировка старого password credential до его замены; ограниченный одноразовый enrolment; роль не меняется |

В B почтовый reset может обслуживать admin/owner и настроенный MFA, но не снимает
их обязательную защиту. Если после сброса остался TOTP — нужен пароль + TOTP;
если удалён единственный UV-passkey и TOTP нет — backup/operator recovery.
Проверяются роль и фактор **при потреблении**, а не только при выпуске ссылки.
Правила A для GET/preview, назначения, A/B, неразличимого ответа запроса,
шифрованной доставки, stable ID/payload и отсутствия resend сохраняются.

Backup codes — независимые случайные высокоэнтропийные значения; в БД только
hash с привязкой к userId и recovery-set. Полный набор показывается один раз
на no-store-странице после step-up или завершения ограниченной настройки.
Он не отправляется письмом. Перевыпуск требует step-up и отзывает прежний набор.
Предлагается разрешить один действительный код без пароля только как основание
ограниченного восстановления; он не создаёт обычную сессию. При его потреблении
отзывается весь старый набор и создаётся единственный enrolment-контекст.
Два одновременных восстановления одним/разными кодами старого набора не успешны.
Это полноценный резервный секрет владения учёткой: его обладатель сможет
установить свой UV-passkey и затем войти. Ограниченный промежуточный контекст
не уменьшает конечные полномочия такого восстановления; выбор требует владельца.

Смысл enrolment ограничен userId, новым поколением, целью настройки и сроком,
не ролью/permissions. Его bearer генерируется CSPRNG из **32 случайных байт**
(256 бит, канонический base64url), а не из userId, времени или счётчика.
В БД хранится только SHA-256 исходного bearer плюс назначение/состояние/срок;
ни строки контекста, ни журнал/ошибка/дамп не сохраняют исходное значение.

Bearer принимается отдельным POST с Origin/CSRF. Атомарный одноразовый обмен
помечает исходный bearer использованным и выдаёт **другой** независимый CSPRNG
секрет из 32 байт для ограниченной Secure/HttpOnly/__Host-cookie, SameSite=Strict,
Path=/, без Domain. В БД также только hash cookie-секрета. Cookie не принимается
как обычная login-сессия; назначение остаётся enrolment. Исходный bearer не
передаётся в URL/query или обычный вход и не может обменяться повторно.
GET не потребляет его. Потеря ответа после обмена не оживляет исходный bearer:
новый операторский выпуск отзывает предшествующие bearer/cookie-контексты.
Завершение настройки атомарно потребляет контекст; повторный запрос, чужая
учётка, просрочка, новое поколение и server API не открывают обход.
Если password credential был скомпрометирован, recovery обязан заменить его
либо оставить отключённым, а не вернуть старый пароль к использованию.

CLI B заменяет текущий аварийный путь, а не оставляет старый `set-password`
альтернативой с меньшим отзывом. Нужны явная цель, причина и журнал без bearer.
Контекст записывается один раз в новый файл 0600 со скрытым/контролируемым вводом;
не в argv, env или обычный stdout. Операции над реальной учёткой и root-файлами
в B не выполняются. Последний active owner сохраняет роль и достижимый путь
повторной настройки даже при недоступной почте; это отдельный сценарий приёмки.

## 6. Транзакции и границы SQL/API

Кандидаты схемы: фактор с pending/active и lastAcceptedStep; pre-auth/reauth-
контексты; proof сессии; recovery-set/код; ограниченный enrolment; счётчики.
Это логические сущности, не обещание восьми отдельных таблиц. Схема/миграция
аддитивны; игровые saves/scores не меняются. Названия уточняются в реализации.

Общий порядок: `access_lock → user → factors/credentials → session/proof →
contexts/codes/mail`, с определённым порядком ID при нескольких user. Все новые
писатели, включая прямой SQL поддерживаемых процедур, согласуются с этим порядком.
Криптография/расшифровка выполняются без удержания блокировок; финальная запись
сравнивает исходный снимок credential/factor/поколения и актуальное время.
Ретраи 40P01/40001 повторяют всю транзакцию, максимум трижды, не обновляют
доказательство и не повторяют внешний HTTP. TOTP-step/code/challenge/session/proof
и отзыв не должны разойтись при crash или инъекции SQL-ошибки.

**Предлагаемая SQL-граница (R2, уточнена в R3).** В текущем `ensureHubRole` есть blanket GRANT
на все public-таблицы. В B его следует заменить явным списком нужных обычному
хабу прав: новая защищённая таблица не должна получать права даже на промежутке
между GRANT и последующим REVOKE. Каждый повтор процедуры выдачи прав обязан
восстанавливать тот же ограниченный результат; DEFAULT PRIVILEGES не обходят его.

Для proof, факторов/guard, recovery-set/codes, enrolment, pre-auth, счётчиков и
резерваций нужны явные правила **SELECT/INSERT/UPDATE/DELETE**, в том числе на
последовательности и функции. Предлагается хранить новые закрытые записи в
отдельной auth-схеме: `gf_hub` не получает её USAGE, прямое чтение или DML.
Существующий public `auth_recovery_guards` сохраняет запрет всех записей;
изменять его могут только разрешённые процедуры/оператор. Журнал не открыт на DML.
Для чтения текущих прав хабу достаточно узкой read-only проверки session/proof,
которая не возвращает секреты и не принимает клиентскую "свежесть" как политику.

| Объект | Прямые права gf_hub |
|---|---|
| Новые закрытые proof/factors/contexts/codes/reservations/counters | Ни SELECT, ни INSERT/UPDATE/DELETE, ни доступ к их sequence |
| Существующий public auth_recovery_guards | Только необходимый A SELECT; INSERT/UPDATE/DELETE запрещены |
| Обычная public session | Требуемое обычному auth SELECT/INSERT/DELETE; **нет** табличного UPDATE, только UPDATE(expires_at, updated_at) для штатного refresh; INSERT не создаёт proof |
| Процедуры записи B | Нет EXECUTE; только отдельная auth-роль/оператор |
| Read-only проверка session/proof | Явный EXECUTE, ограниченный ответ; у PUBLIC нет доступа по умолчанию |

Предлагается отдельная **ограниченная LOGIN-роль auth** с отдельным файловым
паролем и пулом внутри доверенного auth-контроллера. Это не владелец БД:
без superuser/createrole/createdb/bypassrls, без прямого DML закрытых таблиц;
только явный EXECUTE необходимых процедур и минимальные чтения. Обычный
`gf_hub` не является членом этой роли, не наследует её и не может SET ROLE.
Новых сервисов, сетей и портов это предложение не требует; новое подключение
и его секрет всё равно требуют утверждения владельца, рабочая подготовка — D.

Создание/изменение proof и фактора разрешается лишь этому аутентифицированному
SQL-каналу после серверной криптографической проверки; оператор — отдельное
доверенное основание. Процедуры дополнительно проверяют исходный context,
credential/factor, user/session/generation, срок, одноразовость и резервацию.
Сессия, proof и потребление записываются **одной процедурой/транзакцией на одном
подключении**, а не распределённой транзакцией двух пулов. Для UV подходит
только ключ с защищённой записью допуска к усиленному входу; прямой INSERT
обычного passkey через менее доверенный канал не создаёт такой допуск.
Допуск привязан к userId, credential ID и fingerprint криптографически значимых
полей ключа. Замена publicKey/userId/credential ID в обычной таблице не переносит
допуск на новый ключ: snapshot/fingerprint перепроверяются при финальной записи.
Состав допустимых записей обычных account/passkey/session также перечисляется
явно; запись в них не должна косвенно менять защищённую запись или её смысл.

У `session` неизменяемы id, token, userId, securityGeneration, время и
идентификатор выпуска. Ограничение обеспечивается и правами на колонки, и
проверкой перехода строки в SQL; один запрет в Node adapter недостаточен.
Нельзя оставить табличный UPDATE и пытаться отменить его REVOKE одной колонки.
Обновление `expires_at/updated_at` сохраняет прежнюю связь с proof, соблюдает
проверку статуса/поколения и политику срока; оно не изменяет verifiedAt.
Эти права и запреты проверяются заново после `ensureHubRole`, включая PUBLIC
и членство ролей. Обычному хабу не даются TRUNCATE/TRIGGER/права владельца таблицы.

Удаление session (sign-out, expiry, отзыв) атомарно удаляет связанный proof
через защищённую FK/cascade-границу. Перенос proof на другую строку запрещён.
DELETE с последующим INSERT того же id, bearer либо идентификатора выпуска,
UPSERT/MERGE и подстановка token из собственной подписанной cookie не восстанавливают
старое усиление: новая строка не имеет proof, а создать его может только auth-
канал после нового подтверждения. Выпуск сессии использует новый bearer и новый
идентификатор; повторное использование значения не является продолжением сессии.

У PUBLIC и `gf_hub` отозван EXECUTE функций записи; `gf_hub` не может вызвать их
с подставленными `method='uv'`, `verifiedAt`, userId, GUC или SET ROLE. Основание
вызова — проверенная роль подключения, не эти аргументы. В SECURITY DEFINER
учитывается реальная вызывающая роль, а не `current_user` владельца функции;
все ссылки квалифицированы, search_path фиксирован, F4 сохраняется.
Криптографическая проверка остаётся обязанностью доверенного контроллера,
а не утверждением, что SQL-роль сама проверяет WebAuthn. Эта граница не обещает
защиту от SQL-инъекции в самом привилегированном auth-канале, кражи уже выданной
обычной session-cookie или полного исполнения кода доверенного auth-сервера.

До согласия на такую границу не заменять её широкими правами `gf_hub` или
процедурой, принимающей любой `uv=true`. Клиент не задаёт метод/UV/verifiedAt/
поколение. Last-owner и защиты F1–F4 сохраняются.

Новые POST имеют строгую схему, отклоняют неизвестные поля и ограничивают тело
и чтение потока. Профиль не меняет proof, фактор, guard или внутренний MFA-флаг.
События добавления/удаления фактора, recovery и отказов журналируются с причиной
и допустимыми идентификаторами, без секрета, кода, cookie и pre-auth/enrolment bearer.

Все альтернативные Better Auth password/passkey/factor/recovery endpoints
инвентаризируются вместе с server API. Совпадающие действия либо проходят тот же
контроллер и транзакцию, либо явно запрещены. Email OTP, trust-device,
remember-this-device и удаление обязательного MFA в B не включаются.
Новая парольная точка обязана использовать существующий LoginGuard/Origin/CSRF,
а не обходить их новым URL. Клиентские redirects — только фиксированные свои пути.

Флаг B управляет доступностью новых страниц/API, но не выключает уже сохранённое
требование MFA или проверку proof. При выключенных маршрутах обязательный вход
остаётся закрытым. Рабочее появление такой схемы требует заранее подготовленного
enrolment/rollback-плана D; откат на код, игнорирующий MFA, запрещён.

## 7. Принятые параметры B

Параметры R3 приняты в D-066; они не являются полной политикой Q3.

| Параметр | Предлагаемое значение |
|---|---|
| Свежесть step-up | 5 минут, без продления при refresh |
| Pre-auth/reauth/enrolment | 5 минут; pending TOTP-настройка 10 минут |
| TOTP | SHA-1 HMAC, 6 цифр, шаг 30 секунд, окно ±1; секрет 20 случайных байт |
| Backup codes | 10 кодов, каждый не менее 128 случайных бит; показывать один раз |
| Допуски к проверке кода | 5 зарезервированных проверок на контекст, независимо от исхода; дальше он недействителен |
| TOTP после проверенного пароля | 10 зарезервированных проверок за 15 минут по userId/назначению, независимо от новых pre-auth; не блокирует операторское восстановление |
| Анонимная проверка backup code | Отдельная область backup-public: 5 допусков на контекст и 20 за 15 минут на доверенный источник; не расходует userId-квоту обычного MFA |
| Выпуск контекстов после доказательства | 5 за 15 минут по цели/назначению и 20 по источнику; один актуальный enrolment на цель |
| Срок хранения | Контексты не более суток после окончания; истёкшие счётчики удалять ограниченными пакетами |
| Вместимость новых контекстов/счётчиков | По 10 000 строк на область; при заполнении не вытеснять активные защиты, отказать новому действию |

**Допуск предшествует проверке.** До TOTP/backup/enrolment-проверки короткая
транзакция атомарно резервирует одну попытку одновременно во всех применимых
областях. Условия лимита и увеличение выполняются под согласованными блокировками
либо эквивалентной условной записью; сначала COMMIT резервации, затем проверка.
Вне бюджета криптографическая проверка и успешное завершение не допускаются,
даже если код правильный. Запись отказа после проверки — не механизм допуска.

Резервация имеет приватный server-generated ID, назначение и конкретный context;
её нельзя подставить из тела запроса, переиспользовать или передать другому коду/
пользователю. Повтор SQL-транзакции сохраняет исходный ID; повторный запрос с уже
занятым ID не получает второй допуск. Результат проверки атомарно завершает свою
резервацию вместе с целевым действием. Crash, timeout, ошибка verifier/SQL либо
потеря ответа не возвращают потраченную квоту; истечение окна не воскрешает
истёкший context. Криптография не выполняется при удержании блокировок допуска.

**Раздельные области и последствия.** TOTP login/reauth учитывает userId только
после проверки первичного пароля и выдачи валидного pre-auth. Неверный/чужой
pre-auth, email или заявленный userId такого допуска и счётчика не создают.
Backup-public до предъявления действительного кода не делит счётчик с TOTP,
парольным LoginGuard, выпуском MFA-pre-auth или доверенным enrolment. Нельзя
записывать анонимные backup-ошибки как парольные отказы для внешнего рубежа.
Вместимость/очистка также разделены по областям: backup-public не вытесняет
и не исчерпывает резерв строк обычного MFA. Идентичность источника и назначение
области выбирает сервер, не JSON-поле клиента.

Анонимный backup ограничивается постоянными context/source-бюджетами; новые
контексты не сбрасывают source-квоту между процессами/restart. Общую userId-квоту
по одному заявленному email ему не назначать: иначе любой клиент запрёт цель.
Это сознательно иной режим для случайного секрета ≥128 бит, чем для шестизначного
TOTP; общая защита распределённого публичного трафика остаётся C. После проверки
backup-кода лимиты enrolment привязаны к выданному ограниченному разрешению.
Возможность блокировать обычный TOTP знанием верного пароля в пределах auth-
области — отдельно показанное владельцу следствие предложенного userId-бюджета;
нельзя описывать его как доступный без доказательства общий бан учётки.

Счётчики/резервации постоянные и атомарные, переживают restart; одинаковые внешние
ошибки, ограниченные тела/время чтения, отсутствие token/email/OTP в ответах/логах.
Идентификатор источника берётся только из принятого доверенного proxy-контекста;
browser-ID/UA не являются самостоятельным доказательством личности или обходом лимита.
Распределённый перебор TOTP после первичного доказательства проверяется по
userId/фактору, не только по контексту/IP; анонимная backup-область описана отдельно.
Общая HTTP-политика неизвестных учёток и внешних рубежей завершается в C.

## 8. Порядок локальной реализации

1. B1: инвентаризация путей и проверяемые схемы/процедуры/снимки доказательств;
   тестовые миграции, SQL-права, полный отзыв и proof при создании session.
2. B2: двухфазный парольный вход + TOTP и UV-hook passkey; общий guard всех
   потребителей прав и защита альтернативных HTTP/server API.
3. B3: pending/active настройка, step-up, одноразовые backup codes и UI account/security.
   Использовать существующие Popup-компоненты, если понадобятся модальные окна.
4. B4: обычная смена пароля, расширение почтового reset без обхода MFA,
   ограниченное recovery и новая операторская процедура, включая last-owner.
5. B5: полный локальный прогон на **точном кандидате**, native PG-конкуренция,
   адресные мутации, патч/отчёт/промпт ревью; затем отдельно Git/dev/CI.
   Standalone/browser-стенд расширяется проверками B, A сохраняется регрессией.

Это части одного принятого B по D-066. Рабочее применение не разрешено. Новая
необходимая зависимость или изменение принятой модели сначала показываются владельцу.
Нельзя объявить готовым B после одних B1/B2 или только успешного unit suite.

## 9. Приёмка: что должно опровергать ошибки

| Граница | Обязательные негативные/конкурентные проверки |
|---|---|
| Пароль/MFA | Правильный пароль admin/owner без TOTP не создаёт обычную сессию/права; token другого назначения/браузера не завершает вход |
| UV | Реальный verifier: подписанный assertion без UV отвергается для обязательного входа; UV=true проходит. Подмена clientData-флага не помогает |
| Proof | Нет записи/истёк step-up/другой user/session/поколение/исходный bearer — отказ; refresh не обновляет время; SSR и API согласованы |
| Pre-auth/reauth bearer | Генерация каждого через CSPRNG 32 байта, независимость целей и hash-only хранение; угаданный/чужой context с правильным TOTP не завершает вход; правильная cookie с правильным кодом — положительный контроль |
| Криптография | RFC-векторы TOTP, границы времени, replay одного step в двух PG backend; неверный/отсутствующий key-id не снимает MFA |
| Настройка | Pending не считается фактором; пароль не создаёт первый фактор owner; обычный и прямой plugin/server API не меняют фактор без основания |
| Отзыв | Барьеры до/после проверки пароля/UV/TOTP: reset/роль/блокировка/замена фактора не позволяют выпустить новую действующую сессию; F1/F2 остаются зелёными |
| Recovery | Один/два разных кода старого набора, два завершения enrolment, expiry/чужая учётка/повтор CLI: максимум один успех, полный атомарный отзыв |
| Bearer enrolment | CSPRNG 32 байта/канонический формат, hash вместо plaintext в каждой записи и журнале; одноразовый обмен на новый независимый ограниченный cookie-секрет; повтор обмена/завершения отвергается |
| SQL-права | Отдельное настоящее gf_hub-подключение: все запреты матрицы прав, вызов пишущих функций с подставленными аргументами/GUC и SET ROLE auth; подмена обычного passkey не переносит усиленный допуск. Повторить ensureHubRole и все отказы; разрешённый auth-канал и обычное чтение A — положительные контроли |
| Session bearer в SQL | Получить настоящую подписанную cookie attacker обычным входом; под gf_hub попытаться освободить её token и присвоить его строке owner с proof, затем предъявить именно cookie attacker. UPDATE token/id/user/generation/issued identity отвергаются; owner-доступ не появляется. DELETE/повторный INSERT owner с прежними id/token и UPSERT не сохраняют proof. Обычный refresh и вход owner проходят; повторить после ensureHubRole |
| Конкурентный допуск | Два настоящих PG backend и барьер до verifier: параллельных запросов больше context/target-квоты; число допущенных проверок не выше бюджета, правильный код вне него отвергается; внутри бюджета положительный контроль проходит; crash/restart не возвращает резервации |
| Области лимитов | После потока неверных анонимных backup-кодов к owner правильный пароль + TOTP проходит в отдельном browser context **за тем же доверенным IP**, затем за двумя адресами одного IPv6 /64. Сохранить и контроль с другого источника. Проверяется реальный парольный LoginGuard, отсутствие его IP-бана и успешный MFA; backup-бюджет остаётся исчерпан между процессами/restart, userId не заблокирован |
| Q2 | Обычная смена сохраняет факторы и отзывает сессии; email reset не снимает обязательность; единственный UV после reset требует recovery |
| Last-owner | Синтетический последний owner без старых факторов/почты восстанавливает новый фактор через ограниченный операторский контекст, затем входит заново |
| Аварии/лимиты | Ошибка каждой записи откатывает операцию; 40P01/40001 сохраняют исходное proof; restart не сбрасывает лимиты/replay; новые контексты не обходят общий предел |
| Браузер/публикация | SSR/hydration, Origin/CSRF, no-store/no-referrer/noindex на секретных формах; без внешнего QR/ресурсов; закрытая регистрация и выключенные флаги не дают обход |

В приёмке разделения лимитов обязательна адресная мутация: записывать каждый
backup-отказ в парольный LoginGuard для того же нормализованного IP или IPv6 /64.
Она должна провалить именно контроль обычного входа за общим NAT/префиксом,
а не setup или только проверку счётчика. Контроль с другим адресом отдельно
не считается опровержением этой ошибки. Общий сетевой DoS такая проверка не исключает.

Положительные контроли обязательны: рабочий UV/TOTP/login/enrolment и получение
ожидаемых HTTP-запросов. Убрать проверку UV/proof/step replay/atomic consume/guard
должно давать целевой провал, не ошибку импорта или таймаут setup.
Два настоящих PG backend и отдельное gf_hub-подключение нужны для конкуренции/
прав; PGlite их не заменяет. Проверяется повторное применение миграций и полный
список таблиц Docker CI. Нельзя оставлять ожидания старой схемы.

Перед сдачей — `pnpm typecheck`, **полный** `pnpm test`, целевые DB/native/harness
и мутации. Для изменённых handover-документов повторить docs/public checks после
их записи; проверить уникальность всех D-/П-, ссылки, STATE ≤120 строк и состав
публичного кандидата. Встроенные Git-команды тестов разрешены владельцем; иные
Git-операции требуют отдельного согласия. На грязной копии отделить посторонние
ошибки и проверить чистый снимок точного кандидата с frozen lockfile, не скрывать их.

Next build/Chromium/Docker/Actions выполняются только после соответствующего
разрешения по D-049. В CI — один production build и настоящие браузерные проверки
с синтетическими WebAuthn-подписями/виртуальным authenticator. Аппаратный ключ,
реальная доставка, SQL-права/ключи/логи/восстановление рабочей БД проверяются отдельно
перед D. Ревью запускает владелец; публикация и активация не следуют из зелёного CI.

## 10. Решение владельца и оставшиеся границы

D-066 разрешает локальную реализацию B R3: двухфазный контроллер, step-up с
заменой текущей сессии, ограниченные SQL-роль/пул с файловым паролем, параметры
раздела 7 и отдельный ключ факторов. Backup-код без пароля принят как полноценный
резервный секрет аккаунта, дающий только ограниченную настройку перед новым входом.
Коды показываются один раз; в БД только хеши. В интерфейсе обязательно предупреждение
сохранить их офлайн, например на бумаге в безопасном месте. Обычные пароли —
только salted scrypt-хеши. Секрет TOTP хранится отдельно зашифрованным.

Это разрешение разработки и локальных проверок; не утверждение готовности B.
CLI при аварийном восстановлении заменяет пароль, а не оставляет старый доступным.
Публикация/размещение, реальные owner/backfill, рабочие ключи/ротация, миграции,
откат, аппаратные ключи, D-047, полная Q3/CSP/регистрация и активация остаются
отдельными решениями. Политики Q1/Q2/Q3 и почтовая архитектура не переоткрываются.

Источники для будущих проверок: [TOTP/RFC 6238](https://www.rfc-editor.org/rfc/rfc6238)
и [проверка WebAuthn assertion](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion).
Конкретная интеграция сверялась с локальными исходниками Better Auth/passkey 1.7.7;
это чтение кода, не испытание будущего B и не утверждение об уязвимости библиотеки.
