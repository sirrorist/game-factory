## Подтверждённые проблемы

### R1 — P1: работающий просмотрщик сохраняет старый успешный статус после пересборки

**Адрес:** `tests/ui/core/server.ts:68–70`; чтение metadata/report только при старте —
строки 59–62. `() => html` возвращает неизменяемую копию конфигурации, тогда как сервер
`after` продолжает читать файлы из заменяемого каталога.

**Условия и воспроизведение:** взять новое имя прохода, создать baseline и успешный check
для `rogue-destiny`; оставить работающим `pnpm ui:compare rogue-destiny --run ИМЯ --port 0`.
Во втором терминале выполнить `GF_UI_PROFILES=missing-profile pnpm ui:check rogue-destiny --run ИМЯ`.
CLI штатно архивирует старый after/report, пересобирает after, завершает проверку ошибкой.
Перезагрузить страницу оставленного просмотрщика, включая обычный reload браузера.

**Ожидается:** viewer заново читает metadata, проверяет актуальность отчёта, убирает успешную
приёмку и отключает снимки при неполном/упавшем прогоне; обновляет сведения о новой сборке.

**Фактически:** на диске `status: interrupted-or-failed, complete: false, failed: 1`,
а страница после reload по-прежнему пишет «Полный прогон: после — проверки пройдены»,
и режим снимков доступен. В отдельной синтетической пробе после замены HTML версии 2
на версию 3 с другим SHA viewer также показывает старые ref/версию/успех; старый report
уже отсутствует в текущем каталоге. Это позволяет принять непроверенную новую сборку.
Перезапуск самого сервера обновляет конфигурацию, перезагрузка страницы — нет.

**Доказательства:** [штатный CLI, JSON](../test-results/review-bd0b874/cli-stale-visible.json),
[снимок с загруженными iframe](../test-results/review-bd0b874/cli-stale-visible.png),
[другая версия HTML и SHA](../test-results/review-bd0b874/probes.json),
[снимок синтетического сравнения](../test-results/review-bd0b874/stale-viewer-after-rebuild.png).
Скрипты воспроизведения лежат рядом: `cli-stale-visible.mjs`, `probes.mjs`.
При повторении использовать новые имена/каталоги, чтобы не заменить эти доказательства.
Проблема относится к новому общему серверу этого коммита.

### R2 — P2: упавший или прерванный check теряет уже собранную диагностику

**Адрес:** `tests/ui/core/check.ts:57`; накопление только в памяти — строки 35–46,
успешная запись — строка 50. Аналогично статический Superwalk runner пишет результаты
лишь в успешном конце: `tests/ui/targets/superwalk/check.ts:222`.
Обработчик `tests/ui/cli.ts:50` сохраняет только то, что runner успел записать на диск.

**Условия и воспроизведение:** на отдельной копии baseline Snake запустить check с
`GF_UI_PROFILES=phone-landscape,fullhd`. После появления первого PNG изменить только
сгенерированный `after/style.css` (например, дописать CSS-комментарий), дождаться
контрольного отказа по evidence. Отдельно повторить с новым именем, послав SIGINT после
появления четырёх PNG. Исходники игры при этих пробах не менялись.

**Ожидается:** неполный отчёт сохраняет накопленные результаты/ошибки, исходные hashes,
профили, пути к PNG и причину остановки. Успешного статуса быть не должно.

**Фактически:** контрольный отказ срабатывает правильно, но JSON после него содержит только
`status`, `complete:false`, `failed:1`, `exitCode:1`. Измерения четырёх состояний, их errors,
evidence и сообщение «Сборка/инструмент изменились во время проверки» исчезают из отчёта;
последнее остаётся только в stderr. Восемь PNG сохранены, связь с результатами потеряна.
После SIGINT — такой же пустой диагностический итог с `exitCode:130` и четырьмя PNG.
Обычный успешный прогон этих же профилей фиксирует известное переполнение Snake,
но из отчёта аварийного прогона узнать о нём нельзя. Это замечание к сохранению диагностики,
а не новая регрессия Snake.

**Доказательства:** [оба отказа, stdout/stderr и итоговые JSON](../test-results/review-bd0b874/failure-probes.json),
[каталог fatal](../test-results/ui/snake/runs/review-bd0b874-fatal/),
[каталог SIGINT](../test-results/ui/snake/runs/review-bd0b874-sigint/).
Сценарий — `test-results/review-bd0b874/failure-probes.mjs`.
Тест `markInterrupted()` проходит, поскольку подаёт уже наполненный JSON; он не проверяет,
сохраняет ли действующий runner промежуточные данные. Новый общий check подтверждён
исполнением; для Superwalk тот же риск установлен чтением кода, второй аварийный прогон
Superwalk не заявляется.

### R3 — P3: внутренний симлинк обходит запрет выдачи скрытого файла

**Адрес:** `tests/ui/core/server.ts:20–21`; запрет скрытых компонентов проверяется только
для исходного URL на строке 15, но не для пути после `realpathSync()`.

**Условия и воспроизведение:** в новом синтетическом каталоге результата создать файл
`.synthetic-private` с безвредным маркером и `alias.txt`, указывающий на него внутри того же
каталога. Запустить `startComparison`, запросить оба пути через origin before.

**Ожидается:** скрытый файл, прямой URL которого запрещён сервером, также недоступен через
симлинк; оба запроса получают 404.

**Фактически:** `/.synthetic-private` → 404, `/alias.txt` → 200 с содержимым скрытого файла.
Проверка внешнего симлинка в той же пробе вернула 404. Выход за корень этим способом
не продемонстрирован; серьёзность ограничена обходом собственного запрета скрытых файлов
в локальном dev-сервере. Реальные конфиденциальные файлы не создавались и не читались.

**Доказательство:** [HTTP-ответы](../test-results/review-bd0b874/server-http.json),
сценарий `test-results/review-bd0b874/server-http.mjs`. Новая функция `servedFile()`
входит в проверяемый коммит.

## Ограничения

Проверен Chromium с эмуляцией, не физические телефоны, Safari/Firefox, экранная клавиатура,
реальные вырезы, аппаратный GPU, пользовательские настройки масштабирования или физический 4K-монитор.
Видео live сохранены, покадрово не просмотрены. Не выполнялось полное прохождение забега.

Хаб открыт как реальные UI-компоненты в специальной сборке с `mocks.jsx`:
сессия/auth/API/catalog/bridge — образцы, вложенная игра — пустая область.
Это явно написано в README и viewer. Настоящий Next runtime, вход/БД/passkey,
полная связка настоящего хаба и игры и серверная экономика этим ревью не подтверждены.
Iframe-сценарии live — оболочка для размеров и ввода, не настоящий хаб.

Остальные игры проверены только как static/vite-ts стартовые экраны общего CLI,
без проверки прохождения или исправлений их интерфейсов. Известное переполнение Snake
подтверждено у обеих одинаковых сборок; новой регрессией bd0b874 не считается.
`ui:smoke` отдельно не запускался: он жёстко использует прежние каталоги; вместо него
выполнены собственные проверки трёх viewer и verify на именованных проходах.
Windows и сборка Docker не проверялись. Зависимости старых snapshot-сборок взяты из
установленного workspace, как документировано инструментом.

**Вердикт:** визуальные изменения Superwalk и хаба в указанной области прошли независимую
проверку. Общий инструмент требует исправлений R1 и R2 для достоверной приёмки и R3 для
последовательного запрета скрытых файлов. Утверждение прежнего отчёта о полном сохранении
диагностики и отсутствии старого зелёного статуса подтверждено не во всех сценариях.
