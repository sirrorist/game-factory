# Общие правила вёрстки интерфейсов Game Factory

Требование владельца: применять ко всему проекту, чтобы размеры текста и элементов
не приходилось повторно исправлять на каждом большом разрешении. Правило относится
к хабу, играм, меню, HUD, диалогам и dev-инструментам. Оно применяется при новой
вёрстке и изменении существующей; это не заявление о проверке всех старых экранов.

## Масштаб — как в хабе

База — CSS viewport 1920×1080 при стандартном размере шрифта браузера 16 px.
Для стандартного размера шрифта коэффициент `s = max(1, viewportWidth / 1920)`.
Масштаб зависит от доступной ширины документа, а не физического монитора, DPR,
строки браузера или оставшейся высоты окна. Уменьшение высоты не уменьшает текст.

| CSS viewport | Коэффициент | Корневой шрифт | Текст 1 rem | Кнопка 3 rem | Предел панели 37,5 rem |
|---|---|---|---|---|---|
| 1920×1080, Full HD | ×1 | 16 px | 16 px | 48 px | 600 px |
| 2560×1440, QHD / 1440p | ×4/3 | ≈21,333 px | ≈21,333 px | 64 px | 800 px |
| 3840×2160, 4K | ×2 | 32 px | 32 px | 96 px | 1200 px |

Точное существующее правило из [globals.css хаба](../apps/hub/src/app/globals.css):

```css
html { font-size: max(100%, 0.8333333333vw); }
```

`100%` сохраняет нижнюю границу пользовательского размера шрифта. Таблица выше
справедлива для базовых 16 px; не заменять проценты жёсткими `16px`. При увеличенном
пользовательском шрифте фактический root равен максимуму из него и `viewportWidth / 120`.
Указанные соотношения также проверяются [UI-сценариями хаба](../tests/ui/targets/hub/check.ts).

## Что масштабировать вместе

- Размер текста, межстрочные интервалы, иконки и цели управления.
- Внутренние и внешние отступы, gaps, радиусы, обводки и оформление фокуса.
- Минимальную и максимальную ширину панелей, диалогов, карточек и ограничителей контента.
- HUD и вспомогательные подписи: они тоже должны оставаться читаемыми на QHD/4K.

Размеры этих элементов задавать в `rem` или через согласованные токены на его основе.
Базовые 16 px = 1 rem, 24 px = 1,5 rem, 48 px = 3 rem, 600 px = 37,5 rem.
`vw`, `%` и `dvh` задают долю экрана и доступную область; их не умножать повторно.
Например, боковая панель может использовать:

```css
.panel {
  width: clamp(22.5rem, 33.333vw, 37.5rem);
  max-width: 92vw;
  padding: 1.5rem;
}
.action { min-height: 3rem; font-size: 1rem; }
```

Предел 37,5 rem растёт до 1200 px на 4K. Фиксированные `max-width: 600px`,
`font-size: 16px` и `height: 48px` для масштабируемых компонентов так не работают.
Не увеличивать один шрифт внутри прежней маленькой кнопки или панели.
Не применять `zoom` или `transform: scale()` ко всему приложению вместо вёрстки:
это затрагивает координаты ввода, границы, прокрутку и игровую область.

## Адаптив, игры и доступность

- До Full HD масштаб не падает ниже пользовательского базового размера. Телефон
  и планшет получают собственную компоновку; уменьшение всей страницы её не заменяет.
- Пороги смены раскладки могут оставаться в CSS px. Граница в `@media (...rem)`
  не обязана следовать вычисленному корневому rem; проверять фактический viewport.
- Пользовательское увеличение текста не отменять. Разрешать переносы и внутреннюю
  прокрутку; при нехватке места менять раскладку, не прятать подтверждения и действия.
- Цели касания — минимум 48 CSS px. При стандартном масштабе для игр удобно 3 rem;
  на QHD/4K они увеличиваются согласно таблице. Исключения существующего дизайна
  хаба не переносить автоматически на сенсорное управление игры.
- Корневой rem хаба не проходит внутрь iframe. Каждая игра задаёт правило в своём
  документе. Игры с canvas/WebGL масштабируют UI отдельно от игрового мира.
- Шрифт интерфейса не должен менять размер canvas, DPR, физику, таймеры, дистанции,
  камеру или баланс. Safe-area остаётся в единицах, которые возвращает браузер.
- Длительность анимации не зависит от масштаба. Поддерживать сокращение переходов;
  открытая панель не пропускает ввод на поле, включая анимацию закрытия.

## Приёмка изменения

1. Сохранить исходную сборку и доказательства до изменения; не обновлять базу ради
   зелёного результата. Git применять только после отдельного согласия владельца.
2. Проверить все затронутые состояния на 390×844 / 844×390, 768×1024 / 1024×768,
   1920×1080, 2560×1440, 3840×2160. Телефонные профили — с эмуляцией касаний.
3. Измерить root, текст, кнопки, отступы и пределы панели; проверить отношения
   ×1 / ×4/3 / ×2. Одного отсутствия переполнения недостаточно для приёмки масштаба.
4. Проверить resize без перезагрузки и реальные высоты окон 1920×920 / 2560×1280.
   Уменьшенная высота требует прокрутки/компоновки, а не уменьшения коэффициента.
5. Проверить сохранность пользовательского увеличения текста, переносы, доступность
   действий, чтение полного предупреждения и отсутствие обрезки целей касания.
6. Предоставить снимки до/после, отчёт и независимый просмотр. Автоматические проверки,
   визуальный просмотр и физические устройства отмечать отдельно.

Рабочий инструмент и требования к проверяющим — [tests/ui/README.md](../tests/ui/README.md)
и [REVIEWERS.md](../tests/ui/REVIEWERS.md). Частный UI-план не отменяет эти пропорции.
